# 回退协议 (Rollback Protocol)

exec 遇设计缺陷 / check 验证失败 / 一致性冲突 / 契约不通过时，**不回滚 task 状态，只回炉设计**，按本协议分级处理。

> **核心原则**: task 状态保持进行中 (不回退到待处理/就绪)，通过加 subtask 修复 → 回 exec 重派的方式推进。状态机不可逆，修复是「前进式修补」而非「后退式重来」。

---

## 触发场景

以下任一情况触发回退协议：

| 场景 | 触发点 | 典型表现 |
|---|---|---|
| 设计缺陷 | exec 执行中 | 按 design 实现走不通 / 结构漏洞导致阻塞 |
| 验证失败 | check 阶段 | ≥2 轮定点修复仍 FAIL (见 [root-cause-protocol](root-cause-protocol.md)) |
| 一致性冲突 | exec / check | subtask 间实现冲突 / 与契约矛盾 / 与其他 task 接口对不齐 |
| 契约不通过 | check 阶段 | checker 验证发现契约未满足，且非实现 bug 而是契约本身有问题 |

---

## 回退原则

1. **状态不回滚**: task 始终保持「进行中」，不退回「待处理」或「就绪」
   - 状态机单向前进，不可逆 (见 [task-state-machine.md](./task-state-machine.md))
   - 检查未过 ≠ 状态回退：加 subtask 继续跑，是前进式修补

2. **契约不擅改**:
   - **planning 阶段才能改契约** (待处理态可自由调整)
   - exec / check 阶段禁改契约 — 契约是 planning 的产出，exec 层只有执行权，没有修改权
   - 若确需改契约 → 走三级回退，由用户裁定后重新 planning

3. **最小回退原则**: 能一级修就不上二级，能二级就不上三级

---

## 标准流程

```
暂停执行 → 根因分析 → grill 对抗式审查 → AskUserQuestion 确认修复方向 → subtask add 修复任务 → 回 exec 重派
```

### 1. 暂停执行
- 暂停当前在跑的 subtask (未开始的不派，进行中的等它跑完当前轮)
- 标记 task 为「修复中」(逻辑标记，状态仍为进行中)

### 2. 根因分析
- 复用 [root-cause-protocol](root-cause-protocol.md) 的 5 维度探针：
  - ① 需求理解偏差
  - ② 方案设计缺陷
  - ③ 实现 bug
  - ④ 环境或依赖
  - ⑤ 测试本身错误
- 收敛到 root cause，确定可修层

### 3. grill 对抗式审查 (二级及以上必需)
- 调用 [skein-grill](../../skein-grill/SKILL.md) 做对抗式 review
- 从多个维度挑战修复方案，确保不是头痛医头
- 输出：修复方向 + 影响面评估

### 4. AskUserQuestion 确认修复方向
- 二级及以上必须用户确认
- 给用户呈现：根因 + 可选修复方案 + 影响面 + 预估工作量
- 用户选方向后再动手

### 5. subtask add 修复任务
- 在当前 task 下加修复 subtask
- 保留原 subtask 历史 (不删不改，只追加)
- 修复 subtask 明确标注「修复」类型，关联根因

### 6. 回 exec 重派
- 修复 subtask 进入调度队列
- 按 DAG 依赖关系派发执行
- 修复完成后重新 `skein check` 进检查中

## 分级处理

| 级别 | 触发条件 | 处理方式 | 是否需用户确认 |
|---|---|---|---|
| **一级** | 孤立失败，小修复 | 直接补 subtask，回 exec 重派 | 否 |
| **二级** | 一致性冲突 / 方案性缺陷 | grill 审查 → 用户确认方向 → 补 subtask | 是 |
| **三级** | 根本性架构问题 | 可能需要重拆 task / 改契约 / 重新 planning | 是 (用户裁定) |

### 一级：孤立小修复
**条件**:
- 单个 subtask 失败，根因明确 (实现 bug / 环境问题 / 测试写错)
- 不影响其他 subtask
- 不涉及设计变更

**处理**:
- 直接 `subtask add` 加修复子任务
- 回 exec 重派
- 无需 grill，无需问用户

**示例**: 某个函数边界条件漏写 → 加一个修复 subtask 补全。

---

### 二级：一致性冲突 / 方案性缺陷
**条件**:
- 多个 subtask 间实现冲突
- 设计方案有漏洞 (但架构方向没错)
- 契约理解有歧义，需要澄清

**处理**:
1. 暂停执行
2. 根因分析 (5 维度)
3. grill 对抗式审查 → 出修复方案
4. **AskUserQuestion** 给用户看方案，确认修复方向
5. subtask add 修复任务 (可能多个)
6. 回 exec 重派

**示例**: 两个 subtask 对同一数据结构定义不一致 → 统一结构后两边都改。

---

### 三级：根本性架构问题
**条件**:
- 架构方向走不通，需要推倒重来
- 契约本身错误，必须修改
- task 拆分不合理，需要重拆

**处理**:
1. 暂停执行
2. 根因分析 + grill 审查
3. **AskUserQuestion** 呈现问题严重性，给出选项：
   - 选项 A：在当前 task 内大修 (仍保持进行中，加大幅修复 subtask)
   - 选项 B：废弃当前 task，新建 task 重新 planning (原 task 归档或标记为失败)
4. 用户裁定后执行

**注意**:
- 三级回退不自动改契约 — 契约修改必须在 planning 阶段做
- 选 B 新建 task → 新 task 从待处理开始，可自由改契约
- 选 A 大修 → 仍在当前 task 进行中，契约不能动，只能在契约框架内修

---

## 契约修改流程

| 阶段 | 能否改契约 | 说明 |
|---|---|---|
| planning (待处理) | ✅ 可以 | 规划阶段契约未定，可自由调整 |
| ready (就绪) | ⚠️ 受限 | 需重新 confirm (回退到待处理改完再 confirm) |
| exec (进行中) | ❌ 禁止 | 执行层只有执行权，没有契约修改权 |
| check (检查中) | ❌ 禁止 | 验证阶段按契约验，发现契约问题走三级回退 |

**确需改契约的正确姿势**:
1. 走三级回退，AskUserQuestion 说明情况
2. 用户选择「废弃重建」→ 原 task 归档 → 新建 task 从 planning 开始
3. 在新 task 的 planning 阶段修改契约
4. 重新走 confirm → start → exec → check 流程

---

## 反模式

| 禁 | 改为 |
|---|---|
| check 没过就把 task 状态回退到待处理 | 状态保持进行中，加 subtask 前进式修补 |
| exec 阶段发现设计问题直接改契约 | 走三级回退，用户裁定后重建 task 再改 |
| 遇到问题就上三级，大动干戈 | 先分级，能小修就小修，最小回退 |
| 二级回退跳过 grill 直接问用户 | 先做 grill 对抗审查，再把方案给用户选 |
| 修复时删掉原失败 subtask 毁尸灭迹 | 保留历史，只追加修复 subtask |
| 根因分析只查实现层就下结论 | 5 维度全扫，反复不过强制上溯需求/设计层 |
