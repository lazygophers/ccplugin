# ADR 0001 · 看板 DAG 改满铺网格 (放弃「行 = 依赖层」)

- 状态: **Superseded by ADR 0002 (2026-07-28)** —— 结论「分层排布在本项目不可用」已被推翻: 15514px 是 66 行 × 220px 行高造成的, 行高由卡片尺寸定, 不是分层算法定的。缩小节点后同样的层数只占 1/5 高度。本文余下内容保留作演进记录, 不再指导实现。
- 影响面: `assets/webapp/src/new/pages/board.js` 主看板 DAG 视图
- 相关 commit: 待填 (本 ADR 随实现提交)

## 背景 (Context)

主看板 DAG 此前用自研 Sugiyama 分层 + 连通分量货架装箱 (`layoutPacked`)。真实数据 98 task / 143 edge、卡片 340×220、画布宽硬约束 1400px 下，实测画布 **1120×15514px** —— 一根极细长的柱子，用户反复反馈「依旧不是最优解」。

先用 prototype (`.scratch/dag-layout/compare.html`, 已删) 横向对比 8 套引擎: 自研分层装箱 / ELK layered·wrapping·mrtree·force / dagre LR·DOWN。结论是**换算法解决不了**:

| 方案 | 画布 | 填充率 | 交叉 | 超宽 |
|---|---|---|---|---|
| 自研分层装箱 | 1220×15494 | 31.7% | 200 | 0 |
| ELK layered | 11224×6887 | 7.8% | 16 | +9824 |
| dagre LR | 10820×6540 | 8.5% | 14 | +9420 |

ELK/dagre 交叉数漂亮，但它们的前提是画布可以任意宽 —— 一旦施加 1400px 宽约束就得折带，退化回同一根柱子。

诊断出真因是纯算术: 1400px ÷ 340px 卡片 = **只能排 4 列**，而依赖层深 27 层里有 **21 层只含 1~2 个节点**。分层排布要求「一行 = 一个依赖深度」，于是 98 张卡排出 **66 个占用行，其中 44 行只坐 1 张卡**。高度 = 66 × 220 ≈ 15500px，全是分层规则强制的空行。

## 约束 (用户在 grilling 中逐条确认)

1. 画布宽度不许超视口 —— **保留**
2. 卡片不允许缩小 —— **保留**
3. 所有 task 都要画，不许分页 / 聚合 / 折叠 —— **保留**
4. 进页默认要对准正在执行的 task —— **新增**

前三条把可调变量锁死: N=98 固定、卡片尺寸固定、列数固定为 4。高度的理论下界就是 ⌈98/4⌉ 行 —— 除非放弃分层规则，否则动不了。

## 决策 (Decision)

**主看板放弃「行 = 依赖层」，改为拓扑序满铺网格 (`layoutGrid`)。**

- 排序: 连通分量内走 DFS 风格拓扑序 (Kahn + LIFO — 刚解锁的后继紧接父节点铺开)，分量之间连续摆放
- 布局 (当前): **贴合装箱** `layoutCoord` —— 逐张按拓扑序落位, 落点由前驱后继打分选出, y 由 skyline 决定
- 布局 (基座, 供 layoutCoord 取初始序与尺寸): 按行主序填 ⌊(maxW − 2·padX) / colW⌋ 列的网格，一行内并排不同依赖深度的卡；行序**蛇形** (奇数行右→左)，使行末与下一行行首同列，换行只需竖直下降
- 行高: **自适应** —— 卡高按内容 (`cardHeight`)，行高取该行最高，行内顶对齐 (`node.rowH` 供走线找行底)
- 走线: 复用既有正交通道机制，边语义色与箭头不变；扇入 ≥3 的跨行长边走**边捆绑** (`bundleTrunks`) 合流到目标卡左侧的一条主干竖线
- 定位: `focusActive()` 在布局稳定后首次把视口居中到执行中的 task，优先级 `active → check → ready → planning → done`，缺席逐级回退，无匹配退到第一张卡

子任务迷你 DAG (`layoutSubDAG`) 仍走 `layoutPacked` —— 规模小 (个位数节点)，分层可读性在那里是净收益。

## 结果 (Consequences)

实测 98 task (卡片 340×220, 宽 1400):

- 高度 **15514 → 7316px** (理论下界 7320，已压满)
- 占用行 **66 → 33**，无空行
- 回绕边 (被依赖方排在阅读序后面) **0 / 143** —— 分量内按深度排序把方向性保住了
- 布局耗时 **0.7ms** (原分层链在千节点下 27ms)

**代价**: 同一行不再等于同一依赖深度，依赖方向只能靠箭头和边语义色认。这是明确的取舍 —— 用户在 grilling 中直接选了「破，压到 7320px 极限」。

**缓解**: 阅读序 (行主序) 与拓扑序一致，所以边整体仍是往下 / 往右流，不会出现大面积回绕；hover 链路高亮和边语义色 (绿=依赖已完成 / 黄=阻塞·上游可执行 / 红=阻塞·上游被卡) 承担原本由行位置传达的依赖信息。

**走线的后续一轮**: 首版排序只按依赖深度，同深度顺序随意，链上父子被拆散，边成了横跨半张画板的长线。改 DFS 拓扑序 + 蛇形行序后，纯链场景跨格边归零。剩下的长线是**扇入结构本身**: `m8-version` 单点扇入 31，全图 64/143 条边在任何一维网格排布下都不可能与前驱相邻 —— 一维顺序里 31 个前驱不可能都挨着目标。这部分由**边捆绑**解决 (合流到一条主干竖线)，实测长竖线独立通道从每边一根降到 18 根，其中主干一根承载 20 条。

**再后一轮 — 脱离网格**: 用户指出网格「过于规整过于紧凑」，要的是「画布最小 + 基于线条的最优解，卡片在哪由它的前驱后继共同决定」。于是主看板改走**贴合装箱** (`layoutCoord`)：逐张按拓扑序落位，候选落点打分 = 到各邻居距离 + 落点高度 + 回绕惩罚，y 由 skyline 给出。`layoutGrid` 退居其后，只提供初始拓扑序与卡片尺寸。

先试的是纯 barycenter 力导向 (吸引 → 消解重叠 → 竖直压实)，**实测失败**并已删除 —— 面积和边长同时劣化：

| 排布 | 画布高 | 边总长 | 均边长 | 竖直对齐边 | 重叠 |
|---|---|---|---|---|---|
| 满铺网格 | 4994 | 101054 | 707 | — | 0 |
| barycenter 力导向 | 9112 | 181841 | 1272 | — | 0 |
| 贴合装箱 | 4946 | 89095 | 623 | 51 | 0 |

结论: 面积由 skyline 保底 (贴着已放卡长，不留空洞)，位置由邻居打分决定 —— 两个目标要分别用机制保证，交给一个力场同时优化两者会两头落空。千节点 229ms。

**未来若要回退分层**: 需先解掉宽度硬约束或卡片尺寸约束之一，否则会原样退回 15000px 柱子。

## 验证

`assets/webapp/tests/dag-layout.check.mjs` 测试 11 (满铺网格 + 蛇形跨格边为 0: 行数 / 不超宽 / 无重叠 / 边全保留 / 拓扑序单调 / 显著矮于分层)、12 (环兜底)、13 (自动定位优先级 + 回退 + 不出负滚动量 + 空图不抛)、14 (边捆绑: 只捆跨行长边 / 扇入门槛 / 主干贴目标左侧 / 同行近邻不入束)、15 (行高自适应: 卡高各按内容 / 同行顶对齐 / 行高取最高 / 次行按行高推进 / 总高低于等高网格)、16 (贴合装箱: 节点边全保留 / 不超宽 / 零重叠 / 边总长短于网格 / 高度不劣于网格 1.15 倍)。
