# ADR 0001 · 看板 DAG 改满铺网格 (放弃「行 = 依赖层」)

- 状态: Accepted (2026-07-28)
- 影响面: `assets/webapp/src/new/pages/board.js` 主看板 DAG 视图
- 相关 commit: 待填 (本 ADR 随实现提交)

## 背景 (Context)

主看板 DAG 此前用自研 Sugiyama 分层 + 连通分量货架装箱 (`layoutPacked`)。真实数据 98 task / 143 edge、卡片 340×220、画布宽硬约束 1400px 下，实测画布 **1120×15514px** —— 一根极细长的柱子，用户反复反馈「依旧不是最优解」。

先用 prototype (`.scratch/dag-layout/compare.html`, 已删) 横向对比 8 套引擎: 自研分层装箱 / ELK layered·wrapping·mrtree·force / dagre LR·DOWN。结论是**换算法解决不了**:

| 方案 | 画布 | 填充率 | 交叉 | 超宽 |
|---|---|---|---|---|
| 自研分层装箱 | 1220×15494 | 31.7% | 200 | 0 |
| ELK layered | 11224×6887 | 7.8% | 16 | +9824 |
| dagre LR | 10820×6540 | 8.5% | 14 | +9420 |

ELK/dagre 交叉数漂亮，但它们的前提是画布可以任意宽 —— 一旦施加 1400px 宽约束就得折带，退化回同一根柱子。

诊断出真因是纯算术: 1400px ÷ 340px 卡片 = **只能排 4 列**，而依赖层深 27 层里有 **21 层只含 1~2 个节点**。分层排布要求「一行 = 一个依赖深度」，于是 98 张卡排出 **66 个占用行，其中 44 行只坐 1 张卡**。高度 = 66 × 220 ≈ 15500px，全是分层规则强制的空行。

## 约束 (用户在 grilling 中逐条确认)

1. 画布宽度不许超视口 —— **保留**
2. 卡片不允许缩小 —— **保留**
3. 所有 task 都要画，不许分页 / 聚合 / 折叠 —— **保留**
4. 进页默认要对准正在执行的 task —— **新增**

前三条把可调变量锁死: N=98 固定、卡片尺寸固定、列数固定为 4。高度的理论下界就是 ⌈98/4⌉ 行 —— 除非放弃分层规则，否则动不了。

## 决策 (Decision)

**主看板放弃「行 = 依赖层」，改为拓扑序满铺网格 (`layoutGrid`)。**

- 排序: 连通分量内按依赖深度升序，分量之间连续摆放 (相连的卡挨在一起，边不横跨画板)
- 布局: 按行主序填 ⌊(maxW − 2·padX) / colW⌋ 列的网格，一行内并排不同依赖深度的卡
- 走线: 复用既有正交通道机制，`bends: []` / `cross: false`，边语义色与箭头不变
- 定位: `focusActive()` 在布局稳定后首次把视口居中到执行中的 task，优先级 `active → check → ready → planning → done`，缺席逐级回退，无匹配退到第一张卡

子任务迷你 DAG (`layoutSubDAG`) 仍走 `layoutPacked` —— 规模小 (个位数节点)，分层可读性在那里是净收益。

## 结果 (Consequences)

实测 98 task (卡片 340×220, 宽 1400):

- 高度 **15514 → 7316px** (理论下界 7320，已压满)
- 占用行 **66 → 33**，无空行
- 回绕边 (被依赖方排在阅读序后面) **0 / 143** —— 分量内按深度排序把方向性保住了
- 布局耗时 **0.7ms** (原分层链在千节点下 27ms)

**代价**: 同一行不再等于同一依赖深度，依赖方向只能靠箭头和边语义色认。这是明确的取舍 —— 用户在 grilling 中直接选了「破，压到 7320px 极限」。

**缓解**: 阅读序 (行主序) 与拓扑序一致，所以边整体仍是往下 / 往右流，不会出现大面积回绕；hover 链路高亮和边语义色 (绿=依赖已完成 / 黄=阻塞·上游可执行 / 红=阻塞·上游被卡) 承担原本由行位置传达的依赖信息。

**未来若要回退分层**: 需先解掉宽度硬约束或卡片尺寸约束之一，否则会原样退回 15000px 柱子。
