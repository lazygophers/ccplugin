## 没红过的守卫等于没有守卫

### 触发场景
新增代码质量守卫（linter、validator、检查脚本）时。

### 陷阱-正解
**陷阱**：守卫写完就算完，没经过反向验证（植入违规样本看是否报红）。
**正解**：每条守卫都要通过反向验证：植入未登记项 → 确认变红 → 撤回。

### 铁律
- MUST：新守卫必须通过反向验证（激活测试失败 case）
- MUST：反向验证过程：植入违规样本 → 确认检查捕获 → 撤回
- MUST：反向验证失败视为守卫未成功部署

### 反例表
| 禁 | 改为 |
|---|---|
| 守卫完成即停，无反向验证 | 植入样本违规，验证守卫确实报错 |
| 仅验「通过」路径 | 同时验「失败」路径（植入故障） |

## 守卫必须接进测试运行器

### 触发场景
添加新的代码质量检查脚本或验证规则。

### 陷阱-正解
**陷阱**：守卫脚本存在但不被自动运行（如 `webapp/tests/*.check.mjs` 要手动跑），形同虚设。
**正解**：所有守卫直接进 pytest 收集范围（如 `scripts/tests/` 目录），被 `pytest` 自动运行。

### 铁律
- MUST：所有守卫脚本进 `scripts/tests/` 或同等 pytest 收集目录
- MUST：守卫必须暴露为 pytest 可收集的用例或 fixture
- MUST：CI/CD 中 `pytest` 运行时自动执行所有守卫

### 反例表
| 禁 | 改为 |
|---|---|
| 守卫脚本散落各处（如 `webapp/tests/`）需手动跑 | 统一进 `scripts/tests/`，被 pytest 收集 |
| 守卫形式不规范无法 pytest 收集 | 改为 pytest test function 或 conftest fixture |
| 守卫不在 CI pipeline 中 | 确保 CI 包含 `pytest` 完整运行 |

## 单一登记处 + 机械守卫模式

### 触发场景
构建衍生物清单（如配置项、路径规则等）时，其产生来源散落在多个模块。

### 陷阱-正解
**陷阱**：清单项在代码各处产生，与中央清单无强制关联 → 新增项时必然忘记登记，导致清单与实际状态漂移。
**正解**：建唯一登记处（统一常量字典或配置表），让所有清单由它导出；再加一条机械守卫扫「新增产生点却未登记」的场景。

### 铁律
- MUST：衍生物产生来源有唯一的中央登记处（不是各模块分散定义）
- MUST：清单由登记处导出，禁硬编码于数据结构本身
- MUST：加机械守卫，植入未登记的新产生点时当场变红

### 反例表
| 禁 | 改为 |
|---|---|
| 产生点各处硬编码，中央清单独立维护 | 唯一登记处 + 清单由其导出 + 守卫检查遗漏 |
| 人工比对新增产生点和中央清单 | 机械守卫自动扫遗漏 |

### 判据
修完后，下一个人新增产生点但忘登记时，守卫会不会当场变红。如果不会，说明单一登记处尚未真正建立。

## 不对称代价下的保守方向

### 触发场景
判断某个产出「该不该被忽略/该不该被删除」时。

### 陷阱-正解
**陷阱**：少忽略一个衍生物 = 仓库脏一点；多忽略一个真值 = 用户数据不进版本库。两个方向的代价完全不对称，却靠文件名或位置猜。
**正解**：用可验证的客观标准判（「有没有一条命令能从真值重新产出它」），拿不准时一律往安全侧（保留真值）取。

### 铁律
- MUST：忽略/删除的判据必须是可验证的客观标准，不能靠文件名或位置猜
- MUST：拿不准时一律往代价低的一侧取（保留真值 > 保留衍生物）
- MUST：安全侧的断言要逐条独立钉死，不能只测一个代表性样本

### 反例表
| 禁 | 改为 |
|---|---|
| 靠文件名猜「这看起来像衍生物」 | 用「能从真值重新产出」的标准判断 |
| 拿不准时选代价高的一侧（多忽略） | 拿不准时往安全侧取（保留真值） |
| 找一个样本验证就放行 | 所有候选项逐条独立验证 |

### 判据
某个文件是否应该进版本库，不基于名字或位置，而基于「从版本库已有的内容，能否通过某个确定的、可运行的流程重新产出它」。若能，它是衍生物；若不能，它是真值。

## Mypy 守卫：直接跑 strict 模式检查

### 触发场景
为已收敛的类型检查结果建防复发守卫。

### 陷阱-正解
**陷阱**：重新实现一套检测逻辑来验证类型检查器的行为，等于重新发明轮子。

**正解**：防复发守卫直接跑 `mypy --strict` 断言退出码即可。mypy 本身就是最准的检测器，不需要复现它。

### 铁律
- MUST：守卫用 `mypy --strict` 直接验证，禁止自实现检测逻辑
- MUST：守卫结果（退出码）断言为 0（通过）或非零（失败）
- MUST：守卫进入 pytest 收集范围，被 CI 自动运行

### 反例表
| 禁 | 改为 |
|---|---|
| 自写 Python 脚本遍历 AST 检测类型错误 | 调用 `mypy --strict .`，检查返回码 |
| 手动验证不进测试流程 | Pytest conftest 中定义 fixture 或 test function 包裹 mypy 调用 |

### 代价
冷启动约 5~6 秒，接进 pytest。若性能成问题，可延迟到 CI 阶段而非本地开发流。
