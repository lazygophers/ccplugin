# 前端清除遗留就绪态 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标
要解决什么 / 用户价值 / 成功长什么样:

- [ ] 前端状态模型与引擎状态机对齐 —— 引擎侧「就绪」已彻底删除 (`S_READY` 不复存在, `confirm` 吸收原 `start` 职责, 规划完成经人审门直接进「进行中」), 但前端仍把 `ready` 当作一个可显示、可过滤、可排序的合法 task 状态保留着。
- [ ] 消除「看板上存在一个引擎永远不会产出的状态列」这一认知噪音 —— 用户在看板/队列页看到「待执行」列会以为任务会在那里停留, 实际上不会。
- [ ] 成功长什么样: 全前端不存在名为 `ready` 的 **task 状态** (edge kind 与 task 的 ready-to-schedule 布尔标记不在此列, 见边界), 看板列 = 规划中 / 调研中 / 执行中 / 待验收 / 收尾中 / 已完成, dist 产物同步重建。

## 边界
范围内 / 范围外 (非目标) / 已知约束:

- [ ] **范围内**: 前端 task 状态枚举定义与展示元数据 (标签/图标/色变量)、看板列顺序与状态过滤器默认集、后端状态名到前端状态名的映射表、状态色 CSS 变量、帮助页里描述旧 `start` 流程的过时文案、以及上述改动对应的 dist 重建。
- [ ] **范围外 (非目标)**: 引擎侧 Python —— 已在 `concurrency-pools` 完成, 本 task 不碰 `scripts/`。
- [ ] **范围外 (非目标)**: 存量 task.json 的 `status="就绪"` 迁移 —— 已由 `concurrency-pools` 的 s9 提供一次性迁移命令并已在主仓执行完毕, 迁移器内部保留「就绪」字面量是**刻意的**(它要能读到旧值才能迁), 不属于残留。
- [ ] **范围外 (非目标)**: 名字里带 `ready` 但语义不是 task 状态的三处 —— 依赖图的 edge kind (表示「上游已完成、这条依赖已满足」)、task 的 ready-to-schedule 布尔标记 (表示「可被调度器认领」)、以及首页脚手架文案里的「就绪」二字。这三者与 task 状态枚举同名不同义, **误删会造成真实功能回归**。
- [ ] **已知约束**: 前端状态名是后端中文状态名经映射表转换而来, 删枚举必须连映射表一起删, 否则后端若仍传来旧值会静默落到未知状态。
- [ ] **已知约束**: dist 是构建产物, 必须整体重新构建而非手工编辑; Next.js 每次构建生成随机 buildId, 故 dist 必然出现大量 diff, **不能以 diff 大小判断构建是否完整**。

## User Stories

1. As a 看板用户, I want 看板的状态列只出现引擎真的会产出的状态, so that 我不会对着一个永远空的「待执行」列猜测任务为什么不进去。
2. As a 看板用户, I want 状态过滤器的可选项与列一致, so that 我不会勾选一个筛不出任何东西的过滤条件。
3. As a 队列页用户, I want 「待执行」的统计口径与看板一致, so that 两个页面给出的数字不会互相矛盾。
4. As a 新用户, I want 帮助页描述的命令流程与当前 CLI 一致, so that 我照着敲的命令不会因为命令已被删除而报错。
5. As a 维护者, I want 前端状态枚举是引擎状态机的忠实投影, so that 下次引擎改状态时我能靠类型检查发现前端漏改。
6. **(边界情况)** As a 维护者, I want 与 task 状态同名但语义不同的标识符 (依赖边类型 / 可调度布尔标记) 不被连坐删除, so that 依赖图配色与调度预览不会因为一次文本级批量替换而坏掉。
7. **(边界情况)** As a 维护者, I want 存量迁移器内部保留旧状态字面量, so that 它仍然能识别并迁移磁盘上残留的旧数据 —— 迁移器是唯一被允许提及旧状态的地方。
8. **(边界情况)** As a 看板用户, I want 若后端因任何原因仍传来一个前端不认识的状态, 界面不要整块崩掉, so that 一次数据异常不会让我完全看不到看板。

## Testing Decisions
什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:

- [ ] **只测外部行为**: 断言「状态枚举/列顺序/过滤器默认集里不含 ready」这类**对外可见的集合**, 不断言某个具体常量写在第几行、用什么变量名承载。
- [ ] **零残留扫描优先于逐点断言**: 本 task 的本质是「删干净」, 最有效的测试形态是一条扫描式断言 —— 在前端源码中搜索作为 task 状态使用的 `ready`, 结果必须为空。这比逐个文件写断言更抗重构。
- [ ] **扫描必须能区分同名不同义**: 扫描要么按语义位置限定 (只扫状态枚举/映射表/列定义), 要么显式排除已知的三处豁免点并把豁免理由写在断言里 —— 否则这条测试会在每次有人正当使用 `ready` 一词时误报。
- [ ] **codebase 内同类先例**: `concurrency-pools` 的 s8 已经建立了「代码层零残留扫描」的测试模式 (三个扫描测试 + 8 个断言, 落在 `test_zero_residual.py`), 本 task 的扫描应沿用该文件与该写法, 而不是另起一套。
- [ ] **反向验证**: 沿用 s8 的做法 —— 把代码改回保留 `ready` 的旧样子, 确认新加的扫描断言确实转红, 再改回来。不做反向验证的零残留测试可能从头到尾都是绿的假象。
- [ ] **不为纯展示改动写快照测试**: 色变量、文案这类改动靠上面的扫描断言 + 类型检查覆盖即可, 不引入 UI 快照 (维护成本高于收益)。
