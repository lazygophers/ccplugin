# skein-flow redo: 断点续跑 + 重派 subagent — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标

session 会意外结束 —— 窗口关了、上下文爆了、进程被杀。此时被派出去的 subagent 一起消失, 但它们
占的槽还记在盘上: subtask 停在「运行中」, 既不会自己完成也不会自己失败。

后果是**卡死**: 那些槽永远不释放, 调度器认为并发已满, 后续什么都派不出去。想恢复只能人肉去认哪些
是死的、一个个手改状态 —— 而这恰恰是最容易改错的时刻 (刚换 session, 上下文全丢)。

`redo` 就是这个场景的一键出口: 认领残局、复位死槽、接着往下跑。

成功长这样: 新 session 里一句 `redo <tid>`, 卡住的 task 恢复调度并一路跑到闭环, 使用者不需要知道
哪些 subtask 死了、状态该怎么改。

## 边界

范围内 / 范围外 (非目标) / 已知约束:

**范围内**
- [ ] 编排层新增 `redo` 路由 (与 plan / exec / check / finish 并列的第五个首参)
- [ ] 复位该 task 全部「运行中」subtask 为待处理, 重新进入调度
- [ ] 复位后按 task 当前所处阶段续跑完整剩余闭环, 直到 finish
- [ ] `--plan` 子参数: 只把规划推到收敛就停, 不进执行
- [ ] 复位前后向使用者说清动了什么 (哪些 subtask 被复位)

**范围外 (非目标)**
- [ ] 不新增引擎命令 —— `redo` 落在编排层, 状态复位借现有命令拼 (2026-08-01 用户裁定)
- [ ] 不做 agent 存活探测 / 心跳机制
- [ ] 不做自动 redo (定时扫描僵死 task 自动重派) —— 必须由使用者显式发起
- [ ] 不改 subtask 状态机本身

**已知约束**
- [ ] **全部「运行中」一律当孤儿** (2026-08-01 用户裁定)。redo 是使用者显式发起的, 他知道现场没有
  agent 在跑。误判代价 = 重跑一个其实已完成的 subtask, 可接受; 而放过一个死槽 = 继续卡死, 不可接受。
- [ ] 承接上一条: 因此 **redo 期间禁止有 agent 在跑**。若使用者在有活 agent 时 redo, 会把活的也复位,
  造成两个 agent 干同一件事。这一点必须在文档里讲明。
- [ ] subtask 重跑必须幂等 —— 这是 executor 侧既有的要求, redo 只是让它更容易被触发。

## User Stories

极其详尽地穷举, 覆盖功能各方面 (含边界情况):

1. As a 换了 session 的人, I want 一句 `redo <tid>` 就接着跑, so that 我不用先搞清哪些 subtask 死了。
2. As a 换了 session 的人, I want redo 自动复位卡住的槽, so that 调度器不再认为并发已满。
3. As a 换了 session 的人, I want redo 默认跑完剩余全部闭环 (到 finish), so that 我不用一个阶段
   一个阶段地手动推。
4. As a 只想续规划的人, I want `redo --plan`, so that 规划收敛后停下, 不自动进执行。
5. As a 谨慎的人, I want redo 明确告诉我它复位了哪些 subtask, so that 我能核对有没有误伤。
6. As a 谨慎的人, I want redo 在动手前说明「全部运行中都会被当孤儿」, so that 我不会在有 agent
   在跑时误用。
7. As a 使用者, I want redo 对处于任意阶段的 task 都能用, so that 我不必先判断它卡在哪一步。
8. As a 边界情况, task 处于规划态且没有任何运行中 subtask 时, redo 应当等价于续规划而非报错。
9. As a 边界情况, task 已经完成时 redo 应当明确报「已闭环, 无事可做」而不是重跑一遍。
10. As a 边界情况, task 处于验证阶段时 redo 应当重派验证而非退回执行。
11. As a 边界情况, task 处于收尾阶段时 redo 应当重派收尾。
12. As a 边界情况, 没有运行中 subtask 但仍有待处理 subtask 时, redo 直接续调度 (无需复位任何东西)。
13. As a 边界情况, 全部 subtask 都已完成但 task 未闭环时, redo 应推进到下一阶段而非空转。
14. As a 使用者, I want redo 不传 tid 时有明确行为 (处理全部未完成 task 或提示必须给 tid), so that
    我不会撞到一个语焉不详的报错。
15. As a 使用者, I want redo 复位的是 subtask 状态而非删除已产出的改动, so that 我不会丢工作。

## 验收标准

可执行、可核对的完成断言 (逐条):

- [ ] 编排层支持 `redo` 首参路由, 与既有四个阶段路由并列且不冲突
- [ ] `redo <tid>` 把该 task 全部「运行中」subtask 复位为待处理并重新调度
- [ ] 复位后默认续跑完整剩余闭环直到 finish, 阶段间不停顿
- [ ] `redo --plan` 在规划收敛后停止, 不进入执行
- [ ] redo 执行前向使用者说明「全部运行中一律当孤儿」的判定口径
- [ ] redo 执行后列出被复位的 subtask 清单
- [ ] 对规划态 / 执行态 / 验证态 / 收尾态四种起点各有正确行为 (分别为续规划 / 续执行 / 重派验证 / 重派收尾)
- [ ] 已闭环的 task 上 redo 报「无事可做」, 不重跑
- [ ] 无运行中 subtask 时 redo 不报错, 直接续调度
- [ ] redo 只改 subtask 状态, 不删除 / 回滚任何已产出的文件改动
- [ ] 不传 tid 时行为明确 (非语焉不详的报错)
- [ ] 文档写明: redo 期间禁止有 agent 在跑, 否则活 agent 会被误当孤儿
- [ ] 编排层文档经 AI 理解一致性验证 (同一 prompt 连跑 3 次主流程描述一致)
- [ ] 全量测试通过, ruff F/E9 清白

## Testing Decisions

什么算好测试 / 测哪些模块 / codebase 内的同类测试先例:

`redo` 主体是**编排层文案**, 不是可执行代码 —— 它的「正确」等于 AI 读了之后行为对。所以测试分两层:

**文案层**: 沿用本仓库既有的 AI 理解一致性验法 —— 把文件喂给模型问主流程, 连跑 3 次描述一致才算过。
这是本仓库对 skill / agent 文档的既定验收手段, 不新造。

**状态层**: 若复位动作最终落到可执行代码上, 则在 CLI 子进程 + 落盘 task.json 这个既有接缝上测:
构造「有运行中 subtask 的 task」, 跑复位, 断言状态与清单输出。不 mock —— 状态真值在盘上。

**不测**: 不测「redo 之后 agent 有没有真的被派出去」—— 那属于编排纪律 (与「宣称派了 agent 但无
tool_use」同类), 靠流程约束而非自动化测试。

边界场景 (四种起点 + 已闭环 + 无运行中) 逐条列成用例, 因为这些正是最容易被想漏、而使用者又一定会
撞上的情况 —— session 挂掉的时机是随机的, 每个阶段都可能。
