# 分包 Mixin 悬空属性 mypy 债 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标

引擎分层分包时把几个大类拆成了 Mixin 组合。Mixin 里的方法引用的属性由最终组合类持有,
类型检查器看单个 Mixin 时看不到这些属性, 于是报「某某 Mixin 没有某某属性」。

实测约 120 条错误, 全是这同一个模式, 集中在体检、索引、写盘、注入、看板数据源几个模块。
它们不是逻辑错 —— 代码运行时完全正常, 因为属性在组合后确实存在。

代价是**质量门整个失效**: 项目的质量检查命令因此常红, 而一个常红的门等于没有门。它现在正卡着
两个功能已经做完的 task 无法收尾, 更糟的是它把真正的类型错误也淹没了 —— 120 条噪声里混进一条
真问题, 没人看得见。

成功长这样: 质量门恢复常绿, 这一类错误从根上消除而不是逐条压制, 且**以后再拆 Mixin 不会重新
长出来**。

## 边界

范围内 / 范围外 (非目标) / 已知约束:

**范围内**
- [ ] 消除 Mixin 悬空属性这一类错误 (约 120 条, 占总量九成)
- [ ] 处理剩余的零散类型错误 (测试文件里的类型不兼容、多余的忽略注释等)
- [ ] 质量门恢复通过
- [ ] 防复发: 以后新增 Mixin 走同一套写法, 不再产生同类错误

**范围外 (非目标)**
- [ ] 不改任何运行时行为 —— 这是纯类型标注工作, 功能零变更
- [ ] 不重做分包结构 (Mixin 组合方式本身不在讨论范围)
- [ ] 不追求更严格档位 (不开 strict 等更高等级)
- [ ] 不顺手重构被改到的业务逻辑

**已知约束**
- [ ] **禁用整文件忽略与逐行压制作为主手段** —— 那是把门关掉而不是修好, 且会连带掩盖真错误。
      如确有个别无法从根上解决的点, 需单独说明理由并局部处理。
- [ ] 修完必须证明运行时行为没变。这类改动看着安全, 但标注写错位置可能改变属性解析。
- [ ] 错误分布不均: 单个模块就占了约四成。修复顺序应先啃最大的, 早暴露方案是否成立。
- [ ] 本轮环境里 subagent 通道与外部命令通道均出现过长时间不可用, 排期时不要假设可并行派发。

## User Stories

极其详尽地穷举, 覆盖功能各方面 (含边界情况):

1. As a 维护者, I want 质量门常绿, so that 它红的时候我知道是真出事了。
2. As a 维护者, I want 真类型错误不再被噪声淹没, so that 类型检查重新有信息量。
3. As a 正在收尾 task 的人, I want 质量门不再无差别卡住功能已完成的 task, so that 交付不被历史债堵住。
4. As a 以后要新增 Mixin 的人, I want 有一个明确的写法可照抄, so that 我不会重新制造同一类错误。
5. As a 边界情况, 某个属性在不同组合类里类型不同时, 修复方案要能表达这种差异而不是强行统一。
6. As a 边界情况, 若某处错误暴露的其实是真设计问题 (属性根本不该在那访问), 应当如实报出来而不是标注掩盖。
7. As a 审阅者, I want 看得出哪些改动是纯标注、哪些动了实际结构, so that 我能把审阅精力放在后者。
8. As a 维护者, I want 修完的错误数是可核对的, so that 「修好了」不是一句感觉。

## 验收标准

可执行、可核对的完成断言 (逐条):

- [ ] 质量门命令通过 (类型检查 + 测试均绿)
- [ ] Mixin 悬空属性类错误归零
- [ ] 未使用整文件忽略 / 大面积逐行压制作为主要手段; 个别例外逐个写明理由
- [ ] 全量测试通过且**测试数量不减** (证明没有靠删测试换绿)
- [ ] ruff F/E9 清白
- [ ] 运行时行为零变更 (功能测试全绿, 且改动 diff 中不含逻辑分支变化)
- [ ] 防复发手段落地: 新增 Mixin 若重犯同一模式, 质量门会红
- [ ] 修复前后的错误条数有据可查 (修前基数 / 修后为零)

## Testing Decisions

什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:

**这个 task 的验证主体就是类型检查命令本身** —— 它既是问题也是判据, 不需要为「类型标注对不对」
另写测试。跑通即证明。

**真正需要额外保障的是「没改坏运行时」**。纯标注改动的风险恰恰在于它看起来零风险, 于是没人验。
判据是既有全量测试保持绿**且用例数不减** —— 后者是防止靠删测试换绿的机械手段, 本仓库对
「不靠放宽断言换绿」已有明确先例, 这里沿用同一原则。

**防复发要有守卫, 不能靠约定**。本仓库已有源码文本扫描类守卫的先例 (扫死按钮占位符),
同一手法可用于扫 Mixin 写法。守卫**必须反向验证**: 故意写一个违规 Mixin, 确认它真的变红。
没红过的守卫等于没有守卫。

**不测**: 不为每个被修的属性写单元测试。那是实现细节, 且类型检查已经覆盖。
