# 分包 Mixin 悬空属性 mypy 债 — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 测试接缝 (seam)

check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

**接缝 = 既有的质量门命令 (类型检查 + 全量测试), 复用不新建。**

理由: 本 task 的产出定义就是「那条命令从红变绿」, 判据与产出同一。再往下钻 (为每个 Mixin
写类型断言) 是测实现细节, 且类型检查器已经在做同一件事, 属重复投入。

唯一新增的接缝是**防复发守卫**, 它测的是「以后有人重犯会不会被拦住」—— 这是质量门本身覆盖不到的
未来行为, 必须单列。

## 问题的结构

Mixin 方法引用组合类才持有的属性 → 类型检查器孤立看 Mixin 时判定属性不存在。运行时无误,
因为组合后属性确实在。**这是标注问题, 不是设计问题** —— 除非某处访问暴露出属性根本不该在那出现,
那种情况按边界情况单独报, 不混在批量修复里。

## 三种候选解法与取舍

| 解法 | 做法 | 取舍 |
|---|---|---|
| **A. 协议/基类声明属性** | 给 Mixin 声明它依赖的属性 (只声明类型不赋值) | 从根上解决, 顺带把「这个 Mixin 依赖什么」变成显式契约; 每个 Mixin 要写一段声明 |
| B. 逐行忽略 | 每处加忽略注释 | 约 120 处噪声, 且掩盖真错误 —— **PRD 已列为禁用主手段** |
| C. 整文件关检查 | 模块级关闭 | 等于把门关掉, 与本 task 目标直接矛盾 |

**取 A**。B/C 都是把红灯拆掉而不是修车, 而本 task 的全部价值就在于让这盏灯重新可信。
A 的额外收益: 依赖关系变显式后, 下次拆 Mixin 时「我依赖谁」是写出来的, 不是靠读代码猜。

## 执行顺序

按错误数从多到少啃, **最大的模块先做**。理由是解法 A 是否真的成立要尽早证伪 —— 如果它在最复杂的
模块上就不work, 后面几十条改动全部作废, 越晚发现越贵。第一个模块做完先跑一次质量门看降幅是否
符合预期, 再批量推进。

## 防复发

新增 Mixin 若不声明依赖属性就重犯同一模式。守卫用源码文本扫描 (仓库已有先例), 而非依赖类型
检查器自身 —— 因为一旦有人再次用忽略注释压制, 类型检查器就不会报了, 守卫必须能看见「压制」这个
动作本身。

**守卫必须反向验证**: 故意写一个违规 Mixin, 确认真的变红, 再删掉。没红过的守卫等于没有守卫。

## 风险

- **最大风险是「纯标注改动看着零风险所以没人验」**。对策写在 PRD 的 Testing Decisions:
  全量测试保持绿**且用例数不减**, 后者防的是靠删测试换绿。
- 属性在不同组合类里类型不一致时, 强行统一声明会掩盖差异 —— 遇到即按边界情况单独处理并记录,
  禁为了批量整齐而捏合。
