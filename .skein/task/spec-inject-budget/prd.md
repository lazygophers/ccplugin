# spec 注入总预算 800 token 口径统一 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标

spec 库的规则会被自动注入到对话里, 目前有三个注入点: 每轮常驻的会话索引、subagent 启动时的
core 全文、以及显式取全文的命令。用户要求**常驻注入不超过 800 token, 且仍要高效明确**。

现状是三个都超, 而且超得不知不觉:

| 注入点 | 实测 | 名义预算 | 超幅 |
|---|---|---|---|
| 会话常驻索引 | 2363 字符 | 400 token | 约 4 倍 |
| subagent core 全文 | 20652 字符 | 2000 token | 约 7 倍 |
| always 页全文 | 15301 字符 | 1000 字符 | 15 倍 |

超标能一直没人发现, 根因有三条, 缺一条都修不干净:

- [ ] **预算的单位和用户关心的单位不是一回事** —— 守卫量的是字符, 用户和模型付费的是 token。
   中文场景下两者比例接近 1:1, 英文和代码接近 4:1, 同一个字符阈值在不同内容上宽严差四倍。
- [ ] **三个注入点各有各的预算键, 没有一个「总量」概念** —— 每个点单看都「有预算」, 合起来没人管。
- [ ] **超预算只在跑体检时才报, 且报了不挡** —— 它是软约束, 而软约束在没有机械守卫时必然漂移
   (本仓库刚在另一个 task 上踩过同一个坑: 注释里写死的预算数字从 800 涨到 2293 无人察觉)。

成功长这样: 常驻注入实测 ≤800 token 且规则仍然读得懂能照做; 三个注入点的预算在同一张表里
一眼可比; 任何一个超标当场测试变红, 不靠人偶然发现。

## 边界

范围内 / 范围外 (非目标) / 已知约束:

**范围内**
- [ ] 预算口径从字符改为 token, 并给出可复算的换算依据 (不是拍一个系数)
- [ ] 三个注入点的预算收进单一张表, 新增注入点加一行即可
- [ ] 常驻注入压到 ≤800 token, 手段是压缩表达与降级低价值页, 不是截断
- [ ] 机械守卫: 任一注入点超预算即测试失败
- [ ] 现存超标内容实际降下来 (改完就绿, 不是只改阈值)

**范围外 (非目标)**
- [ ] 不改 spec 的 namespace × inclusion 模型 (那是 spec-model-core 的范围)
- [ ] 不改 recall / maintain / degrade 的既有行为语义, 只改它们读的预算值来源
- [ ] 不引入第三方分词器依赖
- [ ] 不改注入的时机与触发条件 (哪个 hook 在什么时候注入, 保持原样)

**已知约束**
- [ ] **注入发生在 hook 热路径** —— 每轮对话都跑。计量方案不能联网、不能有可观的 import 开销,
      这排除了真实分词器 (tiktoken 是 OpenAI 分词器, 对 Claude 也只是近似, 拿不到精度还要付依赖)。
- [ ] **换算系数依赖内容语种**, spec 库是中英混排 + 代码片段。系数必须按本库真实内容标定,
      并且**标定过程要留在测试里可复算**, 否则它就是下一个会漂移的写死数字。
- [ ] 压缩的对象是给 AI 读的规则文本。删得对不对的判据是「AI 读完还能照做吗」, 不是「人读着顺不顺」。
**🛑 预算口径 (2026-08-01 用户裁定): 三个注入点 token 数之和 ≤800。**

这是三个备选口径里最严的一档 (另两档是「只管常驻」与「各自 ≤800」)。它的直接后果必须写在这里,
因为它决定了本 task 大部分的工作量与取舍:

- [ ] **subagent 全文注入现为 20652 字符, 在总和 800 的约束下几乎无处安放** —— 意味着
      executor 类 subagent 将拿不到 core 规则全文, 只能拿索引或极少数最高价值条目。
- [ ] 这与用户同时提出的「需要高效明确」存在张力: 省到极致与说清楚是一对矛盾。
      **本 task 的核心难点即在此** —— 不是删到 800 就算完成, 而是要在 800 内仍让 AI 照做。
- [ ] 若压缩后实测发现规则已无法被照做 (语义断言绿但 AI 复读验证不通过), 应当**回报用户重定口径**,
      而不是自行放宽阈值, 也不是硬压到规则失效。

## User Stories

极其详尽地穷举, 覆盖功能各方面 (含边界情况):

1. As a 每轮都要付这份 token 的使用者, I want 三个注入点合计 ≤800 token, so that spec 不再是大头开销。
2. As a 使用者, I want 压缩后规则仍然能被照做, so that 省 token 不是拿规则失效换的。
3. As a 维护者, I want 预算的单位就是我关心的单位 (token), so that 我不用心算字符换算。
4. As a 维护者, I want 三个注入点的预算在一张表里, so that 我能一眼看出总开销而不是逐个翻。
5. As a 维护者, I want 超预算当场变红, so that 我不必靠偶然读到才发现膨胀。
6. As a 维护者, I want 换算系数的来历可复算, so that 它不会变成又一个没人敢动的魔法数字。
7. As a 边界情况, 中文页与英文页字符数相同但 token 数差数倍时, 守卫应当按 token 判而非按字符判。
8. As a 边界情况, 新增一个注入点时, 应当被迫为它声明预算, 而不是默认无限。
9. As a 边界情况, 内容压不到预算内时应当报出「还差多少 / 哪几页最大」, 而不是静默截断规则中间。
10. As a 使用者, I want 降级挑的是低价值页, so that 留在常驻里的是真正每轮都用得上的规则。
11. As a 边界情况, 预算配置被改小到不合理值 (0 / 负数) 时应当被挡下并说明。
12. As a 谨慎的人, I want 知道压缩后每个注入点实际用了多少 token, so that 我能判断还有多少余量。

## 验收标准

可执行、可核对的完成断言 (逐条):

- [ ] 三个注入点 token 数之和实测 ≤800
- [ ] 三个注入点的预算集中在单一数据结构中声明, 新增注入点需显式声明预算才能生效
- [ ] 预算单位为 token; 字符↔token 换算系数按本库真实内容标定, 标定过程写在测试里可复算
- [ ] 换算系数对中文页与英文页分别验证过, 误差在测试断言的容忍范围内并写明该范围
- [ ] 总和超预算 → 测试失败; 各注入点单项预算亦有守卫; 反向验证过 (撑爆内容能看到它变红)
- [ ] 压缩后 AI 仍能照做 (复读验证); 若做不到则已回报用户重定口径, 未自行放宽阈值
- [ ] 压缩后 spec 规则语义未丢: 已被现有测试钉住的规则条目逐条仍在
- [ ] 压不进预算时给出可执行的报错 (还差多少 + 最大的几页), 不静默截断
- [ ] 预算配置为非正数时被挡下并给出原因
- [ ] 现存三处超标全部降到各自预算内 (不是只调高阈值)
- [ ] 全量测试通过, ruff F/E9 清白

## Testing Decisions

什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:

**核心是一条机械守卫**: 直接断言各注入点的 token 数 ≤ 其预算。仓库里刚为同类问题建过先例
(判定文案的篇幅守卫), **沿用那套做法**: 阈值取实际值加少量余量, 余量小于「新增一整段」的量级,
大于「一次措辞微调」的量级, 并且**守卫必须反向验证** —— 撑爆内容确认真的变红, 没红过的守卫
等于没有守卫。

**换算系数要有自己的测试, 不能只是一个常量**。它是本 task 唯一的估算环节, 也是最容易悄悄失真的
地方。测试应当拿本库真实的中文页与英文页各跑一遍, 断言换算结果落在声明的误差带内 —— 这样系数
的来历就固定在测试里, 后来人改它必须同时面对证据。

**语义不丢靠既有断言 + AI 复读**。现有测试已逐条钉住不能丢的规则, 压缩后它们必须原样绿, 且
**不允许靠放宽断言换绿**。另外沿用仓库对提示词类文件的既定验法 (同一 prompt 连跑 3 次描述一致,
并与压缩前对照) —— 注意该验法依赖外部命令通道, 本轮该通道曾长时间不可用, 若届时仍不可用,
**如实标记为未验证, 禁以推断代替**。

**不测**: 不测具体措辞、段落顺序、页面文件名。那些是实现细节, 而改它们正是本 task 要做的事。
