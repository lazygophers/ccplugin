## 目标

要解决什么 / 用户价值 / 成功长什么样:

- [ ] **master 全量测试回绿** —— 干净 master 实测 19 failed / 314 passed, 全部清零

      本轮已因此出过一次假绿, 这是本 task 的真正驱动力, 不是单纯的测试维护
- [ ] **不靠放宽断言换绿** —— 每条红都修被测对象或测试入口, 禁删断言、禁 skip、禁 xfail 蒙混

## 边界

范围内 / 范围外 (非目标) / 已知约束:

**范围内** — 干净 master 上实测的 19 条失败, 分三组独立根因:

| 组 | 数量 | 根因 |

| A | 13 | 前端迁移删掉了旧 SPA 源码目录, 三个 node 侧测试文件仍在 import 它 |
| B | 4 | `claim` 命令新增必填 phase 参数时, 同步改了一个测试文件却漏了另一个 |
| C | 2 | 前端迁移对服务端入口的改动, 触发了上一轮刚立的两条守卫 |

**范围外**:

- [ ] 前端迁移本身的功能正确性 —— 迁移由另一会话完成并已提交, 本 task 只补测试侧的适配, 禁重做迁移
- [ ] `concurrency-pools` 的并发池重构 —— 本 task 是它的前置基线清理, 禁顺手改并发面
- [ ] 给 Next.js 侧新建独立测试体系 —— 用户已裁定走「测试指向 TS 源」路线, 不另起炉灶

**已知约束**:

- [ ] **用户裁定 (2026-08-01): A 组测试改为指向迁移后的 TS 源, 而非指向构建产物, 也不删除。**

  代价是要给 pytest 侧引入一层 TS 执行依赖, 这个代价用户已接受。
- [ ] C 组两条守卫红得**完全正确** —— 它们抓到的正是设计意图内的违规。
  **禁通过给守卫加豁免来消红**, 必须修被守的那一侧。守卫本身零改动。
- [ ] 三组都在同一 worktree 内作业, 属共享环境, 必须串行推进, 禁并发。

## User Stories

极其详尽地穷举, 覆盖功能各方面 (含边界情况) —— 穷举本身就是逼出边界情况的机械手段:

1. As a 开发者, I want 在干净 master 上跑全量测试拿到全绿, so that 我开新任务时任何一条红都必然是我自己引入的。
2. As a 开发者, I want 前端逻辑的测试直接跑在 TS 源上, so that 我改了 TS 源忘记构建时测试立刻红, 而不是悄悄测着旧的构建产物。
3. As a 开发者, I want TS 执行通道的失败信息可读, so that 测试红的时候我能分清是「被测逻辑错了」还是「TS 没跑起来」—— 这两者的修法完全不同。
4. As a 开发者, I want 迁移前后被测行为逐条对齐, so that 「改了入口」不会变成「顺手少测了几条」。
5. As a 维护者, I want `claim` 的所有测试调用点都跟上必填参数的变更, so that 下次再改命令签名时, 一次全量搜索就能找全调用点。
6. As a 维护者, I want 服务端入口新增的属性登记进类型声明块, so that 类型检查继续覆盖它, 而不是被一条压制注释绕过去。
7. As a 维护者, I want 服务端入口写盘的产物登记进衍生物清单, so that 它被正确纳入忽略与重建规则, 而不是变成游离的未登记写盘点。
8. As a 维护者, I want 修完之后守卫仍能反向验红, so that 我确认它们是在真守着, 而不是被这次修改改到失效。
9. As a 开发者, I want 边界情况: TS 执行通道在缺少依赖的环境下给出明确的缺失提示, so that 新克隆仓库的人知道要装什么, 而不是看到一堆 module not found。
10. As a 开发者, I want 边界情况: 修完 A 组后旧 SPA 目录的残留引用被搜干净, so that 不留下第二批同样根因的红。

- [ ] 全量测试中 **0 个新增 skip / xfail**
- [ ] A 组: 三个 node 侧测试文件均改为指向迁移后的 TS 源, 全仓搜不到对已删旧 SPA 目录的引用
- [ ] A 组: 迁移前后被测行为逐条对齐, 差异 (若有) 在本 PRD 内说明理由
- [ ] B 组: 全仓搜索确认 `claim` 的测试调用点无一遗漏
- [ ] C 组: 两条守卫零改动 (git diff 为空), 修的全在被守一侧

## Testing Decisions

什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:

- [ ] **本 task 的产出就是测试本身**, 因此「验收」= 这些测试在真实被测对象上跑绿, 且**验证过它们还能红**。
  没红过的测试等于没有测试 —— 这条在本仓刚沉淀过, 本 task 是它的直接应用。
- [ ] **A 组的接缝取 TS 源模块的导出函数**, 与迁移前一致 (迁移前取的是 JS 源模块的导出)。
  取这个接缝的理由: 它是迁移前后唯一没变的东西 —— 逻辑被换了语言但导出契约没变,
  所以对齐它就能证明「换语言没换行为」。往上取 (走 HTTP 打整个页面) 会把渲染层的变化混进来,
  那是迁移本身的事, 不归本 task。
- [ ] **C 组不新增测试** —— 守卫已经存在且已经在报红, 要做的是让被守一侧合规。
  新增测试反而会稀释「守卫零改动」这条验收。
- [ ] 先例: 本仓已有对类型检查结果做整体断言的测试, 以及对源码做 AST 扫描找违规写盘点的测试,
  两者都是「守卫型测试」的现成写法, A 组若需要新守卫可照抄其结构。

## 执行期发现 (main 复核记录)

**B 组「第三处遗漏」确实存在, 共三处。** 都不在那 19 条红里 (所以不会自己暴露), 但同属
「`claim` 加必填参数时没跟上」这一根因, 放着就是下一个人踩的坑。**已并入 c1 一并修掉**,
理由是修法只有三行, 单开 subtask 的调度开销大于工作量本身。

**归属更正**: main 曾一度认定这三处是自己搜出、执行 agent 漏报。**这是错的** —— b1 的 agent
回传延迟到达, 其内容准确列全了三处, 而 main 自己那轮搜索只找到两处 (漏了手动冒烟脚本里的
第二个调用点)。**准确的记录是: agent 搜得比 main 全, main 的复核反而有遗漏。**
这条留着, 是因为把「复核者一定比执行者可靠」当默认假设本身就是个偏差。

| 处 | 性质 | 为什么没被那 19 条红暴露 |
|---|---|---|
| 手动冒烟脚本里的调用点 (两处) | 真坏了, 但 pytest 从不收集该函数 | 它不是测试, 是给人手跑的脚本 —— 没有任何自动化覆盖它 |
| CLI 探针清单里的调用点 (一处) | 测试仍绿, 但**探针被静默弱化** | 该测试只断言「不挂住 stdin」, 参数错误退出同样满足这条, 于是它再也走不到真实代码路径 |

第二处是更值得记的一类: **断言太弱的测试在依赖变更后会继续显绿, 同时悄悄失去覆盖。**
它不会红, 所以不会有人来看它 —— 只能靠这种顺藤摸瓜的搜索发现。

另记: b1 的执行 agent **产出正确但未回传也未标 done** (worktree 里改动已在, 5 passed)。
main 复核实测后代为收尾。这与本轮此前 exec-m3 的表现是同一模式, 已非孤例。

### C 组收尾记录 (main 亲验)

| 验收项 | 实测 |
|---|---|
| 两条守卫绿 | 6 passed |
| 守卫文件 git diff | 空 (硬验收守住) |
| `# type: ignore` 数量 | 8 → 8, 零新增 |
| 全量 | 19 failed → **13 failed** (B/C 两组全清, 剩 A 组 13 条) |

**反向验红由 main 补跑 —— 执行 agent 未回传实录** (dispatch 里写明「不能只写『验过了』」仍未照做):
- 衍生物守卫: 摘掉刚补的登记项 → `serve.py:build_app(): 'index.html'` 报红; 还原 → 5 passed
- 类型守卫: 摘掉一个属性声明 → `"DataSource" has no attribute "_spec_meta" [attr-defined]` 报红; 还原 → 1 passed

**一处需要留证的判断**: c1 的修法是往 `DataSource` 的 **Protocol 体**里加三个方法桩, 而不是
dispatch 里指定的 `TYPE_CHECKING` 属性声明块。乍看撞上了 `mypy-mixin-debt` 立的禁忌
(「Mixin 继承 Protocol 会把桩塞进 MRO, 运行时遮蔽真实现」)。

**实测确认不构成违规**: `DataSource` 全仓纯作类型注解用 (`build_app(board: "DataSource", ...)`),
**没有任何类继承它** —— 生产实现是结构化鸭子类型传进去的。没有继承就没有 MRO 注入, 那条禁忌
的前提不成立。`DataSource.__mro__` 实测只有 `Protocol/Generic/object`。

留这条是因为: **规则的适用前提比规则本身更容易被忘掉。** 下次有人看到「Protocol 里有方法桩」
就照着禁忌打回, 会误伤一个正确实现。
