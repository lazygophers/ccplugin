# 精简 judge _CTX 注入文案 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标

每一轮用户输入, 判定文案都会被原样注入一次。它是**每轮都付费**的常驻成本, 所以篇幅本身就是它的
质量指标之一。

现状: 这份文案已膨胀到约 2400 字符, 约为源码注释里自己声称的预算的三倍, 而注释还停在旧数字没更新
—— 也就是说超预算这件事**没有任何机制会发现**, 全靠人偶然读到。

膨胀的成因不是内容太多, 是同一件事被说了三遍: 判定要写原因 (规则一遍、论证一遍、前缀规则再一遍)、
证据裁决与脚本自动注入的证据串重复、短句授权的解释与证据串里的解释重复。冗余不只费 token, 它还
稀释重点 —— 读到第五遍「要写原因」时, 真正的判据反而被淹了。

另外, 上一轮手工编辑删掉了一条被测试钉住的示例, 测试现在是红的。

成功长这样: 文案篇幅砍掉一半以上, 每条已被测试钉住的语义一条不丢, 测试全绿, 并且**再膨胀会当场
变红**而不是靠人偶然发现。

## 边界

范围内 / 范围外 (非目标) / 已知约束:

**范围内**
- [ ] 压缩判定注入文案篇幅, 消除跨段落的重复表述
- [ ] 修复因上一轮手工编辑而变红的断言
- [ ] 新增篇幅守卫: 超预算即测试失败
- [ ] 校正源码注释里已失真的预算数字, 使其与实际、与守卫阈值三者一致

**范围外 (非目标)**
- [ ] 不改判定的**语义** —— 判据、落地路径、开放意图词汇表、跨 session 续跑规则一条不动, 只改表达
- [ ] 不改信号检测逻辑 (词表、正则、短句阈值)
- [ ] 不改前缀规则要求的判定行格式
- [ ] 不处理插件市场缓存滞后 (注入生效的是缓存副本, 与本 task 的文案编辑是两件事)

**已知约束**
- [ ] 一批语义已被测试逐条钉死, 压缩时**一条都不能丢**: 判定行格式模板、每条模板都带原因、意图
      清单声明为非穷举、示例里含「续跑在途 task」这类非新建意图、跨 session 续跑不等于新需求、
      落地路径三条各自的判据与拿不准时的取向、注入文案里不得出现转义漏出的反斜杠。
- [ ] 这份文案的读者是 AI 不是人。删得对不对的判据是「AI 读完行为还一样吗」, 不是「人读着顺不顺」。
- [ ] 预算是软约束 (超了不会崩), 所以必须有机械守卫, 否则必然再次悄悄膨胀 —— 这次就是这么来的。

## User Stories

极其详尽地穷举, 覆盖功能各方面 (含边界情况):

1. As a 每轮都要付这份 token 的使用者, I want 文案篇幅显著变短, so that 常驻开销降下来。
2. As a 使用者, I want 压缩后 AI 的判定行为不变, so that 省 token 不是拿判准率换的。
3. As a 维护者, I want 同一条规则只在一处说, so that 以后改规则不用找齐三处。
4. As a 维护者, I want 文案超预算时测试变红, so that 我不必靠偶然读到才发现膨胀。
5. As a 维护者, I want 源码注释里的预算数字与守卫阈值一致, so that 注释不会再变成误导。
6. As a 维护者, I want 已被测试钉住的语义在压缩后逐条仍在, so that 压缩不是偷偷删规则。
7. As a 边界情况, 上一轮手改造成的红测试要么改文案补回语义、要么改断言, **必须显式二选一**,
   不允许含糊带过。
8. As a 边界情况, 若某条语义确实该删 (而非该压), 需要连同它的断言一起删并说明理由, 不允许留一个
   永远为真的空断言。
9. As a 使用者, I want 判定行格式模板在压缩后仍然一眼可抄, so that AI 不会因为格式变含糊而漏写。
10. As a 使用者, I want 意图词汇表仍然是开放的, so that 「续跑某 task」这类真实意图不会被硬塞进
    三选一。
11. As a 边界情况, 压缩不得引入转义字符问题 (曾踩过: 反引号转义漏出反斜杠, 注入后是怪字符串)。

## Testing Decisions

什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:

这份文案已经有一套成熟的测试做法: **对文案文本本身做语义断言** —— 每条断言钉住一条不能丢的语义,
并在 docstring 里写清「为什么这条不能丢」(通常是踩过的坑)。本 task **沿用这套做法, 不新造**。

**新增的唯一一类断言是篇幅守卫**。它必须是机械的: 直接断言长度上限。理由是这次膨胀正说明「靠人
读到才发现」不成立 —— 而篇幅恰好是少数几个能机械判定的质量维度之一。阈值取压缩后的实际值再留
一点余量, 留太多等于没守。

**守卫必须反向验证**: 把文案临时撑爆, 确认测试真的变红, 再改回来。没红过的守卫等于没有守卫。

**语义不变要靠 AI 复读验证, 不靠断言**。断言只能证明关键词还在, 证明不了「AI 读完行为一样」。
沿用仓库对提示词类文件的既定验法: 同一 prompt 连跑 3 次, 主流程描述一致才算过 —— 并且要与压缩前
的描述做对照, 只自比一致是不够的 (三次一致地读错也叫一致)。

**不测**: 不测文案的具体措辞、段落顺序、标题名。那些是实现细节, 一改就红, 而改它们正是本 task
要做的事。
