# Web 设置面板接线 + 清理死按钮 + 删除按钮转红 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标

Web 看板上有三处按钮在骗人:

- [ ] **页头的齿轮 (设置) 按钮点了没反应** —— 它有图标、有 hover 效果、有 title, 唯独没有任何行为绑定。
   后端读写配置的端点早就在跑了, 前端一行都没消费。用户看到一个设置入口, 点下去什么都不发生。
- [ ] **任务详情页的操作区有一排按钮只会弹「开发中」** —— 编辑 / 就绪 / 开始 / 提交验收 四个, 全是弹窗
   占位。它们和旁边真能用的「确认规划」「删除任务」混在一起, 用户没法从外观分辨哪个是真的。
- [ ] **删除任务按钮显示为蓝色** —— 它明明标了危险样式, 却被主题选择器覆盖成了普通蓝。最危险的动作
   长得和最普通的动作一样。

三条共同的病根是**界面在承诺它做不到的事**。修的方向也统一: 要么把承诺兑现 (设置面板接线),
要么把承诺撤回 (删死按钮), 要么把警示恢复 (删除转红)。

成功长这样: 齿轮点开能看到并改动工作区配置且立刻生效; 详情页操作区剩下的每个按钮点了都真的做事;
删除按钮一眼就是红的。

## 边界

范围内 / 范围外 (非目标) / 已知约束:

**范围内**
- [ ] 页头设置按钮接线: 打开配置面板, 读取当前生效配置, 可改可存, 存完即时反映
- [ ] 配置面板覆盖工作区常规配置项 (并发上限 / 自动提交 / 保留天数 / worktree / Web 服务 / spec 预算)
- [ ] 移除任务详情页操作区全部「开发中」占位按钮 (编辑 / 就绪 / 开始 / 提交验收)
- [ ] 删除任务按钮在明暗两套主题下都显示为危险色 (红)

**范围外 (非目标)**
- [ ] 不新增后端配置端点 —— 读写端点已存在, 本 task 只接线
- [ ] 不实现被删掉的那四个按钮的真实功能 (编辑任务 / 手工改状态) —— 删除即撤回承诺, 要做是另一件事
- [ ] 不改配置项本身的语义、默认值、校验规则
- [ ] 不动看板右侧详情面板的删除按钮 (它已经是红的)
- [ ] 不做配置的历史版本 / 回滚 / 导入导出

**已知约束**
- [ ] **hooks 配置一律不可远程写** —— 它的值是 shell 命令, 开放远程写等于开放远程执行。面板对它
      只能只读展示或干脆不展示, **禁做成可编辑**。这是安全边界不是取舍。
- [ ] 配置的生效值可能被环境变量覆盖, 面板显示的应当是**生效值**而非文件里的字面值; 二者不一致时
      用户有权知道。
- [ ] 后端只接受已知配置键, 面板提交的结构必须与之对齐, 否则改动会被静默丢弃。
- [ ] 页头是全局共享的, 设置入口在任何页面都要能用, 不能只在某一页生效。

## User Stories

极其详尽地穷举, 覆盖功能各方面 (含边界情况):

1. As a 使用者, I want 点齿轮能打开设置面板, so that 我不用去翻配置文件改并发数。
2. As a 使用者, I want 面板里看到的是当前**生效**的配置值, so that 我改之前知道现状。
3. As a 使用者, I want 改完点保存能立刻生效, so that 我不用重启服务。
4. As a 使用者, I want 保存成功/失败都有明确反馈, so that 我不会以为存上了其实没存。
5. As a 使用者, I want 在任何页面 (概览 / 看板 / 队列 / 规范 / 归档) 都能点开设置, so that 我不用先切页。
6. As a 使用者, I want 面板能关掉且不影响当前页面状态, so that 我不会因为改配置丢掉看板上的选中项。
7. As a 谨慎的人, I want 知道哪些配置项被环境变量覆盖了, so that 我不会白改一个不生效的值。
8. As a 边界情况, 我填了非法值 (并发数填 0 / 负数 / 文字) 时应当被挡住并说明原因, 而不是存成坏配置。
9. As a 边界情况, 后端保存失败 (磁盘只读 / 配置文件被占) 时面板应报错并保留我填的内容, 不清空。
10. As a 安全相关方, I want hooks 配置在面板里不可编辑, so that 别人碰不到我的工作区就不能让它执行命令。
11. As a 使用者, I want 详情页操作区里剩下的按钮点了都真的做事, so that 我不用逐个试哪个是假的。
12. As a 使用者, 删掉那些占位按钮后 I want 操作区布局不塌, so that 剩余按钮仍排得整齐可点。
13. As a 使用者, I want 删除任务按钮是红的, so that 我不会把它当成普通操作误点。
14. As a 暗色主题用户, I want 删除按钮在暗色下同样是红的, so that 警示不因主题而消失。
15. As a 明色主题用户, I want 切主题后删除按钮仍是红的, so that 修复不是只对一套主题成立。
16. As a 边界情况, 全站其它危险按钮 (若有) 应当和删除按钮同色同待遇, 不出现两种「危险」外观。

## 验收标准

可执行、可核对的完成断言 (逐条):

- [x] 点页头齿轮打开配置面板 (此前点击零反应)
- [x] 面板展示的配置值 = 后端返回的生效值 (含环境变量覆盖后的结果)
- [x] 面板可编辑常规配置项并保存成功, 重新打开面板显示新值
- [x] 保存后配置文件真实落盘, 且服务端后续读到的是新值 (不需重启)
- [x] 保存成功与失败各有明确用户反馈, 失败时用户填的内容不丢
- [x] 非法值 (并发上限为 0 / 负数 / 非数字) 被挡下并给出原因
- [x] hooks 相关配置在面板中**不可编辑** (只读展示或不展示), 面板不会提交 hooks 字段
- [x] 设置入口在全部页面均可用
- [x] 任务详情页操作区已无任何点击后仅弹「开发中」的按钮
- [x] 任务详情页操作区剩余按钮 (确认规划 / 删除任务) 功能不回归, 布局不塌
- [x] 删除任务按钮在明色与暗色两套主题下均渲染为危险红
- [x] 前端无 console 报错 (含「函数未导出 / 未导入」这类悬空引用)
- [x] 全量测试通过, ruff F/E9 清白

## Testing Decisions

什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:

三条改动的可测性差别很大, 分开对待, **不为了凑覆盖率给不该测的东西写测试**:

**配置面板 —— 测数据往返, 不测 DOM**。真正会坏的是「面板提交的结构与后端认的键对不上」以及
「hooks 被提交上去」。前者用后端既有的配置端点测试接缝覆盖 (提交一份面板形状的负载, 断言落盘
结果); 后者必须有一条专门的断言钉死 —— 那是安全边界, 靠人眼复查不够。面板长什么样、用什么控件,
不测。

**死按钮移除 —— 用源码扫描守卫**。这类改动的失败模式是「删了一处漏了一处」, 而不是逻辑错。沿用
仓库已有的源码文本扫描先例, 断言前端源码里不再出现「开发中」这类占位提示。它同时能防以后有人
再手滑加回来。

**删除按钮颜色 —— 不写自动化测试**。CSS 层叠的对错靠断言 class 名毫无意义 (class 一直都在, 错的是
优先级), 而真正验证它需要跑浏览器渲染, 代价远超收益。这一条靠明暗两套主题各人眼看一次确认, 并在
验收标准里写死是两套主题都要看。

沿用仓库既有的 JS 导出/导入静态扫描守卫 —— 新增的面板代码若出现未导出 / 未导入的悬空引用, 测试
全绿也会在运行时炸, 这个坑本仓库已经踩过两次。
