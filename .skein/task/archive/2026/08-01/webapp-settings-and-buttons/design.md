# Web 设置面板接线 + 清理死按钮 + 删除按钮转红 — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 1. 三条改动的性质完全不同

放同一个 task 是因为它们共享同一个改动面 (Web 前端的按钮层), 分三个 subtask 是因为性质不同:

| 改动 | 性质 | 风险 |
|---|---|---|
| 设置面板接线 | 新增功能 (前端消费已有端点) | 中 —— 涉及安全边界与数据往返 |
| 删死按钮 | 纯删除 | 低 —— 唯一风险是删漏 |
| 删除按钮转红 | 一处样式优先级修正 | 低 —— 但不修根因就会复发 |

**取舍**: 三者不合并成一个 subtask。合并会让「纯删除」和「新增功能」共享同一次验收, 后者出问题
会连累前者回滚。

## 2. 设置面板: 消费已有端点, 不新建

后端已有一读一写两个配置端点: 读端点返回**生效值** (含环境变量覆盖), 写端点只认已知配置键、
逐键做类型强制、并硬拒安全禁写键。

**取舍: 面板不做客户端类型转换, 只做非法值拦截**。后端本就要做强制转换 (它是唯一真值源), 前端
再做一遍就有了两套规则, 迟早分叉。前端只负责在明显非法时 (并发上限 0 / 负数 / 非数字) 提前拦住
并说明原因 —— 那是给用户的即时反馈, 不是数据正确性的保障, 保障归后端。

**取舍: 全量提交, 不做增量 diff**。写端点的设计就是接收完整嵌套结构。前端算 diff 只提交改动项,
会引入「哪些字段没提交等于不改, 哪些等于清空」的歧义, 而收益仅是省几百字节。

### hooks: 安全边界, 不是配置项

hooks 的值是 shell 命令, 后端把它列入远程禁写名单 —— 允许远程写等于允许远程执行任意命令。

面板的正确姿势是**根本不渲染它的编辑控件**, 且提交的负载里**不带这个字段**。理由: 渲染成只读,
用户会追问「为什么不能改」, 答案需要一段安全解释; 渲染成可编辑再由后端拒绝, 则是把安全依赖放在
后端兜底上 —— 后端确实会兜, 但前端不该主动去撞这堵墙。

这一条要有测试钉死, 不能只靠代码评审。

### 环境变量覆盖的显示

读端点返回的是生效值。若某项被环境变量覆盖, 用户在面板里改文件值是白改。

**取舍**: 「显示的是生效值」必须做到; 「标出哪些被覆盖」若后端现有返回不足以区分, 则不为此扩后端
—— 那属于本 task 明确划在范围外的「新增端点/字段」。此时退化为在面板上写一句口径说明 (显示的是
生效值, 可能来自环境变量)。这是有意的降级, 不是遗漏。

## 3. 载体: 全局页头的模态, 不是新页面

设置入口在页头, 页头被所有页面共享。做成路由页会导致「点设置 → 离开当前页 → 关掉后回不到原来的
看板选中状态」。做成模态则当前页面状态原样保留 —— 用户故事里明确要求了这一点。

## 4. 死按钮移除: 撤回承诺, 不是隐藏

四个按钮 (编辑 / 就绪 / 开始 / 提交验收) 全部**删除**, 不是禁用、不是加「暂未实现」提示。

理由: 禁用态按钮仍然占位、仍然暗示「以后会有」, 而这四个功能没有排期。留着它们的唯一效果是让
用户每次都要重新确认一遍哪些是假的。

删完操作区剩两个真按钮 (确认规划 / 删除任务), 需确认布局不塌 —— 原布局依赖若干按钮撑开宽度。

**为什么用源码扫描而不是人肉 grep**: 这类「删漏一处」的失败不会让任何测试变红, 也不会在常走的
路径上暴露 —— 只有点到那个漏网按钮的用户才会撞上。扫描测试同时兼作回归防线。

## 5. 删除按钮转红: 修根因, 不是加 `!important`

根因是**选择器优先级**: 主题选择器组合出的规则比危险色规则更具体, 于是在该主题下把危险色覆盖成
了普通按钮底色。

**取舍**: 不用 `!important` 压。那是把一次优先级冲突换成一条以后没人敢动的规则 —— 下一个想给危险
按钮做定制的人会撞上同样的墙, 且这次连覆盖手段都没有了。正确做法是让危险色规则的优先级不低于
主题规则 (给它同等的主题限定, 或调整声明顺序与特异性), 使两套主题下都成立。

**必须两套主题都验**: 只在一套主题下看对了就收工, 正是这个 bug 当初产生的方式。

## 6. 已知风险

- **面板与后端键结构对不齐**: 提交了后端不认的键 → 静默丢弃, 用户以为存上了。这是本改动最阴的
  失败模式 (无报错、无红测试), 必须用往返测试覆盖: 提交面板形状的负载, 断言落盘结果。
- **悬空引用**: 本仓库已踩过两次 (函数没导出 / 没导入, 测试全绿但运行时炸)。新增面板代码必须被
  已有的静态扫描守卫覆盖。
- **样式修复只在一套主题成立**: 见 §5。
- **删死按钮删漏**: 见 §4, 靠扫描测试兜。

## 测试接缝 (seam)

check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

**主接缝 = 后端配置端点的 HTTP 往返** (现有服务端路由测试的既有做法, 复用不新建)。

理由: 面板的「对不对」最终等价于两件事 —— 提交的结构后端认不认、hooks 有没有被提交上去。两件都
能在这个接缝上断言, 且完全不碰 DOM: 换控件、改布局、调文案都不会让测试变红。在 DOM 层断言则相反,
几乎必然过期。

**次接缝 = 前端源码文本扫描** (仓库既有先例, 复用不新建), 只承担两件扫描性质的事: 占位提示零残留、
新增引用无悬空。

**不新建接缝**: 不测 CSS 渲染结果 (见 §5, 需真浏览器, 代价远超收益), 不测模态的开关动画 / 焦点行为。
删除按钮的颜色靠明暗两套主题各人眼看一次, 这一点写进验收标准而不是伪装成自动化测试。
