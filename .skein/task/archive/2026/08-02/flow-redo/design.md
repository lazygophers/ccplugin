# skein-flow redo: 断点续跑 + 重派 subagent — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 1. redo 落在编排层, 不落引擎

`redo` 与 plan / exec / check / finish 并列, 是编排层的第五个首参路由 (2026-08-01 用户裁定)。

**为什么不做成引擎命令**: 引擎已经有能改 subtask 状态的命令, 复位不需要新语义 —— 只是「把这些
subtask 打回待处理」。真正新的东西是**编排决策** (认哪些是孤儿 / 复位后从哪个阶段续 / 续到哪停),
而那本来就是编排层的职责。多加一个引擎命令只会让「谁负责判断」这件事变模糊。

代价: 复位动作要用现有命令拼, 拼法必须写清楚, 否则每次 redo 拼得不一样。这一点在编排文档里用固定
步骤锁死。

## 2. 孤儿判定: 全部「运行中」一律当孤儿

**取舍** (2026-08-01 用户裁定): 不做心跳、不做 started 时长阈值、不做候选清单让用户勾。

理由是这道题的代价不对称:
- 误判一个其实还活着的 → 重跑一个 subtask, 浪费一点时间
- 放过一个死槽 → 槽永远不释放, 调度器认为满槽, **整个 task 卡死**

而且 redo 是**使用者显式发起**的 —— 他敲这个词的时候就知道现场没有 agent 在跑。阈值方案表面上更
安全, 实际是拿一个拍脑袋的数字去猜一件使用者本来就知道答案的事, 还会在长任务上误判。

**代价必须写进文档**: redo 期间不能有 agent 在跑。否则活 agent 被复位, 会出现两个 agent 干同一件
事、互相覆盖改动。这不是可以靠代码防住的 (编排层看不见 agent 存活), 只能讲明白。

## 3. 起点分流: 从哪续

redo 不预设 task 卡在哪一步, 按它**当前所处阶段**决定续什么:

| task 当前阶段 | redo 做什么 |
|---|---|
| 规划中 | 续规划到收敛 (无运行中 subtask 可复位, 直接续) |
| 执行中 | 复位运行中 subtask → 重新调度 → 跑完剩余闭环 |
| 验证中 | 重派验证 (不退回执行 —— 执行已完成, 退回是倒车) |
| 收尾中 | 重派收尾 |
| 已闭环 | 报「无事可做」, 不重跑 |

关键取舍: **验证态不退回执行态**。session 在验证阶段挂掉时, 执行产物是完好的, 退回执行等于把做完
的活重做一遍。要重做的只有验证本身。

## 4. --plan: 只到规划停

默认跑完剩余全部闭环 —— 因为 redo 的使用场景就是「接着做完」, 停在中间需要人再喊一次, 与初衷相左。

`--plan` 是给另一种情况留的口子: 使用者只想把规划补收敛 (比如要先看看规划成什么样再决定做不做),
不想它自动开工。

## 5. 透明度

redo 会动状态, 而使用者刚换 session、上下文全丢, 最没有能力判断动得对不对。所以两件事必须说:

1. **动手前**: 声明判定口径 (全部运行中一律当孤儿), 让使用者有机会喊停
2. **动手后**: 列出被复位的 subtask 清单, 让使用者能核对有没有误伤

不做交互式确认 —— redo 的本意是一键接着跑, 多一轮往返与初衷相左 (这一点在孤儿判定那道选择里已经
定过)。

## 6. 不做的事

- **不做 agent 存活探测**: 编排层没有可靠手段知道一个 subagent 是否还活着; 做半吊子探测比不做更糟,
  因为它会制造「系统知道」的错觉。
- **不做自动 redo**: 定时扫描僵死 task 自动重派, 听起来省事, 实际是在无人看管时并发派 agent, 风险
  与收益完全不成比例。
- **不回滚已产出的改动**: redo 只改状态。已经写出来的代码留着 —— 那是上一轮的劳动成果, 且 subtask
  重跑本来就要求幂等。

## 7. 已知风险

- **活 agent 被误复位**: 见 §2, 无法用代码防, 只能文档讲明。这是本设计最大的已知缺口, 是为了换取
  「不卡死」而主动接受的。
- **拼法漂移**: 复位靠拼现有命令, 若文档写得含糊, 每次 redo 拼得不一样。对策: 固定步骤写死, 并用
  AI 理解一致性验证 (连跑 3 次描述一致) 确认它不会被读出多种解法。
- **重跑非幂等 subtask**: 若某个 subtask 的实现不幂等, 重跑会产生重复产物。这是 executor 侧的既有
  要求, redo 只是让它更容易被触发 —— 不在本 task 修, 但要在文档里点名。

## 测试接缝 (seam)

check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

**接缝 = 编排文档的 AI 理解一致性** (本仓库对 skill / agent 文档的既定验法, 复用不新建)。

理由: redo 主体是编排层文案, 它的「正确」等于 AI 读完之后行为对。把文件喂给模型问主流程, 连跑 3 次
描述一致才算过 —— 尤其要验「四种起点分别续什么」不会被读出歧义, 那是本设计最容易读错的一段。

**次接缝 = CLI 子进程 + 落盘 task.json** (仅当复位动作最终落到可执行代码时才需要)。构造一个带运行中
subtask 的 task, 跑复位, 断言状态与清单输出。不 mock —— 状态真值在盘上。

**不新建接缝**: 不测「redo 之后有没有真的派出 agent」。那属于编排纪律 (与「宣称派了 agent 但无实际
tool_use」同类), 靠流程约束而非自动化测试 —— 编排层本就无法自证它派了 agent。
