# agent 文档正向化 — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 1. 转写规则 (先定范式, 再批量套用)

否定式按性质分四类，每类一种固定转法：

| 类型 | 原式 | 转法 | 例 |
|---|---|---|---|
| 唯一合法路径 | 禁 A（言下之意只能 B） | **只 B** | 「禁全仓回滚」→「撤销改动只用 `git checkout -- <自己改的具体文件>`，逐个点名」 |
| 前置条件 | 禁未 X 就 Y | **先 X 再 Y** | 「禁未 Read 就改」→「改前先 Read 目标文件」 |
| 归属边界 | 禁做 A（A 归别人） | **A 归 <谁>** | 「禁自行加 subtask」→「补 subtask 归 main」 |
| 能力事实 | 无 Write/Edit 权限 | 保留原样 | 陈述事实而非约束，无正向等价 |

**why 一律保留**：原文写了理由的（如「全仓回滚会静默抹掉并发 subtask 的改动」），转写后理由跟在破折号后原样带上。理由是 agent 遇到文档没覆盖的情形时唯一的判断依据，删了等于把规则降级成口令。

## 2. 去重的三类公共条目

跨 9 个文件重复出现、措辞各异的：

1. **公共铁律引用**（Recursion Guard / 无 AskUserQuestion / 生命周期脚本权限）——统一为同一句 + 同一个 spec 锚点。
2. **工具失败标记** `[工具失败: <原因>]`——统一措辞，各 agent 只补自己特有的失败场景。
3. **缺信息回传** `需要: <问题>`——统一为「标 `需要: <问题>` 回传，由 main 转达用户」。

去重原则：**保留一处完整表述，其余引用它**，而不是九处都删到只剩关键词——agent 文件是各自独立加载的，删光了读者看不到约束。

## 3. 执行顺序 (为什么不是九个文件并行改)

先在 3 个高密度文件（checker 24 处 / specer 19 / dedup 17）上把范式跑通并沉淀成对照表，再拿这张表套用到其余 6 个。

**取舍**：九文件并行分派给多个 agent 会更快，但措辞风格必然分裂——同一条「工具失败」在三个人手里会写出三种句式，反而制造新的不一致。这个任务的价值恰恰在一致性，所以串成两段。

## 4. 可能性分支

- **触发条件**：转写过程中发现某条约束本身就是错的/过时的。
  **做法**：原样保留 + 在回传里单独列出，交 main 判断是否另开 task 修。本 task 只改措辞，不夹带语义修正。

## 5. 难逆决策

**语义等价优先于措辞美观**。遇到正向表达明显更绕、更长的条目，保留否定式并列入豁免清单——把话说清楚比凑满「零否定词」重要。验收看的是豁免清单有没有理由，不是命中数是否归零。

## 测试接缝 (seam)

check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

- **唯一接缝：项目 CLAUDE.md 规定的 AI 理解度检查**（`cat <文件> | claude -p --bare "<问题>" --output-format stream-json 2>/dev/null | jq -r ...`）。
  这是本任务最高、也是唯一有意义的接缝：文档改写的真实外部行为就是「AI 读完能否正确理解触发场景与主流程」，而这条命令直接测它。措辞级单测会锁死措辞、阻碍后续优化，不写。
  端点 ConnectionRefused 属抖动，重跑而非当结论；predictability 按 CLAUDE.md 要求同 prompt 连跑 3 次比对主流程描述。
