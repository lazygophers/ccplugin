# hook 层一 hook 一文件 — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 现状与为什么改

hook 层现有的划分口径是「按**协议位置**切, 不按文件大小切」—— 于是同属一类协议位置的 hook 被塞进
同一个模块: 一个模块装了 4 个 hook, 另一个装了 3 个, 其余已经是一 hook 一文件。

这个口径与本层最重要的一条设计**自相矛盾**。分发表刻意存「模块:函数」字符串而不是函数对象,
全部理由就是懒加载 —— 只 import 被选中的那一个。但模块粒度是 4 个 hook 合一时, 调一个 hook
仍要付同模块里另外 3 个 hook 的常量、正则、helper 的加载成本。拆到一 hook 一文件, 懒加载才真正
兑现: **这次改动不是推翻原设计, 是让原设计生效**。

顺带解决的可读性问题: 现在要找某个 hook 的实现, 得先读分层说明才知道它被合并进了哪个模块。

## 共享面 (已勘察, 拆分方案的依据)

- 装 4 个 hook 的模块里, 那条最长的私有 helper 链 (frontmatter 解析 → 规格发现 → glob 匹配 →
  上下文注入) **只有其中一个 hook 使用**, 整条随它走, 不进公共零件模块。
- 真正跨 hook 共用的只有两个常量, 各被两个 hook 引用 —— 这两个下沉到公共零件模块。
- 装 3 个 hook 的模块切面更干净: 三个 hook 各自的正则与常量互不交叉, 直接一分为三。

## 关键取舍

- **纯搬迁, 行为一字不变**: 不借机重构逻辑、不合并看起来重复的代码 (两个模块里各有一份
  frontmatter 解析, 形似但服务不同格式, 本次**不动**)。理由同前几次合并任务: 一旦开始改写,
  就无法用「与旧版本逐函数比对」证明零变更, 验收失去抓手。
- **共用常量下沉而非复制**: 两份副本会各自漂移, 这类判据一旦不一致就是隐蔽 bug。
- **只被单 hook 用的 helper 不下沉**: 公共零件模块一旦开始收留「反正也算通用」的东西就会变杂物间,
  而它是被所有 hook import 的, 变胖直接反噬热路径。
- **非 hook 模块不动**: 分发、公共零件、钩子执行器、复杂度判定纯函数都不是 hook, 不适用一 hook
  一文件的口径, 本次不碰。
- **两个拆分串行而非并行**: 二者都要改同一张分发表, 并行必冲突。用依赖串起来, 不靠运气。

## 风险与护栏

对外契约是插件配置里写死的入口路径与全部子命令名 —— 一个都不能改。搬迁最典型的事故是
import 接线断了但静态检查看不出来 (分发表存的是字符串, IDE 与类型检查都跳不过去, 拼错要到
运行时才炸)。护栏就是**逐条实调全部子命令**, 这也是本次的测试接缝。

另一条护栏是热路径开销: 分层说明里记着历史基准值, 沿用同一测法比对, 不得劣化。

## 测试接缝 (seam)
check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

**接缝 = 从命令行逐条实调全部子命令。**

选它的理由: 这是 hook 层真实的调用面 (harness 就是这么调的), 最靠外部行为; 一次覆盖 import
接线、分发表改指、函数可达性三类搬迁事故 —— 而这三类正是纯搬迁唯一可能出的错。一个接缝够了。

不选的接缝: 函数级直调 (绕过分发表, 恰好测不到最容易错的那一环)、断言某常量定义在哪个文件
(测的是实现细节, 正是本次要改的东西)。
