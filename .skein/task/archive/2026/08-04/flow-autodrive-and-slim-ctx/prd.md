# 判定走 flow 后自动推进 + 注入文案瘦身 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标
要解决什么 / 用户价值 / 成功长什么样:
- [ ] 判定走 flow 之后真的往下跑 —— 建完 task 不停手, 同一回合续到下一个必须用户拍板的门为止
- [ ] 每轮注入的判定文案变短, 省下的是每一句用户输入都要付的固定成本
- [ ] 短不以丢规则为代价: 砍的是重复与举例, 不是判据

## 边界
范围内 / 范围外 (非目标) / 已知约束:
- [ ] 范围内: 每轮注入文案的内容与篇幅、「判了 flow 之后该做什么」这条规则的补全、篇幅守卫阈值同步下调
- [ ] 范围外: 不改信号检测的词表与判据逻辑 (那是另一套东西, 本次只动注入文案); 不改任何 CLI 命令; 不改确认门本身
- [ ] 约束: **确认门不能被绕过** —— 自动推进的终点是「遇到需要真实用户动作的门就停」, 不是一路跑到底
- [ ] 约束: 注入层是全仓最热的代码, 每句用户输入都跑, 不得引入新的重 import 或文件读取
- [ ] 约束: 篇幅守卫是唯一会在文案膨胀时报警的机制, 压缩后阈值必须跟着降, 否则守卫失效
- [ ] 约束: 未初始化分支的两段文案与诊断命令逐字同步, 动它们要两边一起改 —— 本次不动

## User Stories
极其详尽地穷举, 覆盖功能各方面 (含边界情况) —— 穷举本身就是逼出边界情况的机械手段:
1. As a 用户, I want 提一个改动请求后 AI 判定走 flow 就直接把规划跑出来, so that 不用再喊一次「继续」
2. As a 用户, I want 自动推进撞上需要我拍板的门时停下来问我, so that 不会有人替我批准我的规划
3. As a 用户, I want 每轮注入的固定开销更小, so that 长会话里省下的额度用在真正的工作上
4. As a 用户, I want 判定行格式与落地路径判据在压缩后仍然完整, so that 省 token 不换来判错档
5. As a 用户 (边界), I want 已有在途 task 时的续跑指引不被压掉, so that 新 session 不会把老任务当新需求重建
6. As a 维护者, I want 篇幅守卫在压缩后仍能对「新增一整段」报警, so that 文案不会又慢慢涨回去
7. As a 维护者 (边界), I want 运行配置这类低频信息不占用每轮预算, so that 固定开销只留真正每轮都要读的东西
8. As a 用户 (边界), I want 判定是 inline 或纯答问时不被自动推进裹挟, so that 小改和问答不会被硬拽进流程

## 验收标准
可执行、可核对的完成断言 (逐条):
- [ ] 注入文案里明确写出「判了 flow 之后要继续做什么、做到哪里为止」, 不再停在建 task 那一步
- [ ] 自动推进的终点被写明是「需要真实用户动作的门」, 且注明不得代替用户批准
- [ ] 每轮注入总字数较改动前显著下降, 且下降幅度可量化报出
- [ ] 判定行格式模板、写原因的要求、落地路径三条及其判据、拿不准时的取向, 压缩后全部还在
- [ ] 在途 task 的续跑指引仍在
- [ ] 篇幅守卫阈值已随压缩同步下调, 且余量仍小于文案里最短的一个独立小节
- [ ] 注入层无新增的重 import 或额外文件读取
- [ ] 全量 pytest 不低于基线 410 passed / 0 failed

## 验证方式
每条验收标准的验证手段与通过标准 (plan 阶段必填):
- [ ] 规则补全: 读注入文案 —— 通过标准: 含「建 task 后继续跑」与「停在用户门」两层意思, 且有禁止代批准的字样
- [ ] 篇幅下降: 改动前后各量一次总字数 —— 通过标准: 有明确下降, 数字写进收尾报告
- [ ] 规则零丢失: 逐条比对压缩前后的判据清单 —— 通过标准: 判定行模板 / 原因要求 / 三条路径 / 拿不准取向 / 续跑指引 全部保留
- [ ] 守卫有效: 把阈值与压缩后实际值对比 —— 通过标准: 余量小于最短小节字数, 加一段必触发
- [ ] 热路径无劣化: 读改动后的注入代码 —— 通过标准: 无新增模块级重 import, 无新增文件读取
- [ ] 回归: `uv run pytest plugins/tools/skein/scripts/tests/` —— 通过标准: 410 passed / 0 failed
- [ ] 端到端: 构造一次命中改动信号的输入喂给注入层 —— 通过标准: 输出含新规则且总长符合新预算

## Testing Decisions
什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:
- [ ] 好测试 = 对**注入文案这个产物**断言: 它含哪些必备语义、总长多少。这是注入层真实的对外输出
- [ ] 篇幅守卫必须是机械阈值而非注释里的数字 —— 注释不会失败, 文案曾在无人察觉时从 800 涨到 2293
- [ ] 新增一条断言: 注入文案含「判了 flow 之后继续推进」的语义, 否则本次修的问题会静默回退
- [ ] 不测: 文案的具体措辞、某句话在第几行 —— 属实现细节, 措辞本就要随经验调整
- [ ] 先例: 仓内已有针对注入文案的必备语义断言与双阈值篇幅守卫, 沿用同一形态
