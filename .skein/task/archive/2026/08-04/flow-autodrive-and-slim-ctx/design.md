# 判定走 flow 后自动推进 + 注入文案瘦身 — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 缺陷根因: 规则写到一半就断了

注入文案里关于 flow 的指令只有一句半 —— 「第一个动作是建 task, 不是直接改」。它把**起点**规定死了,
却对**之后做什么**只字未提。AI 照做: 建完 task, 规则用尽, 于是停手报告「已建 task」。

这不是 AI 不听话, 是规则本身缺了后半截。补的不是约束而是延续: 建完之后继续跑规划,
一路推到第一个必须真实用户动作的门 (规划确认) 为止。

## 自动推进的终点必须写死

「一路跑下去」若不写终点就是危险的 —— 规划确认门要求真实用户动作, 自动推进撞上它必须停,
而不是自行代批。这条要与推进规则写在同一处, 中间不隔别的内容: 分开写等于给「只读到前半句」
留了口子, 而本次修的恰恰就是「只读到前半句」这个故障模式。

判定不是 flow 时 (inline / 纯答问 / 并入现有 task) 不适用推进规则 —— 推进的对象是 flow 这条路径本身。

## 瘦身: 砍重复, 不砍判据

每轮注入由两块拼成, 两块都在讲判定行的格式与写原因的要求 —— **同一条规则说了两遍**。
这是最大的一块冗余, 也是砍起来零风险的一块: 保留一份完整的, 另一份缩成指针。

第二块冗余是举例。判定行给了四个例子, 但格式模板本身已经自解释, 例子的边际价值随条数递减 ——
留最能区分档位的两条, 其余删。

第三块是低频信息占了每轮预算: 运行配置逐轮注入, 但它只在真正跑 flow 时才有用, 且几乎从不变化。
改成有在途 task 时才注入 —— 没有在途 task 就说明这轮不在流程里, 配置对当前判定毫无输入。

**不砍的**: 判定行格式模板本体、写原因的要求、落地路径三条及其各自判据、拿不准往重的一侧取、
在途 task 的续跑指引。这些是判档的全部依据, 少一条就是判错档, 省下的 token 换不回来。

## 篇幅守卫必须跟着降

守卫是双阈值的 (两块各守各的), 刻意不合并 —— 合并后一块的余量会掩盖另一块的膨胀。
压缩后如果阈值不动, 守卫就形同虚设: 文案能重新涨回原大小而不报警。所以阈值随实际值同步下调,
余量继续卡在「小于文案里最短一个独立小节」的量级, 保证「新增一整段」这个最小膨胀场景必触发。

这条容易在收尾时被忘掉, 因为不改阈值测试也是绿的 —— 绿灯反而是守卫失效的症状。

## 关键取舍

- **补规则而非加约束**: 故障是规则缺后半截, 不是 AI 违规。加「禁止停手」这类否定式指令对
  已经读完全部规则的模型没有增量, 反而占篇幅 —— 直接把后半截补上更短也更有效。
- **两块结构保留, 不合并成一块**: 合并能再省一点, 但双阈值守卫依赖两块独立存在。为省几十字
  牺牲膨胀检测能力不划算 —— 文案膨胀是这里被验证过的真实历史故障 (曾从 800 涨到 2293 无人察觉)。
- **运行配置改成条件注入而非删除**: 它在真跑 flow 时确实有用 (并发数决定派几个 agent), 删了会
  让执行期少一份依据。按「有无在途 task」开关, 拿掉的正好是它无用的那些轮次。
- **不动信号词表**: 词表是另一条独立的演进线, 每次调都要重跑误报评估。本次是文案任务, 混进去
  会让「篇幅下降多少」这个验收失去干净的对照。

## 测试接缝 (seam)
check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

**接缝 = 注入文案这个产物本身** (沿用既有的「必备语义断言 + 双阈值篇幅守卫」形态)。

选它的理由: 本次全部改动最终都体现为「注入出去的那段文本长什么样」—— 规则补没补全、
篇幅降没降、判据丢没丢, 三类验收全落在这一个产物的内容与长度上。一个接缝全覆盖。
既有测试已经是这个形态, 本次只增一条断言 (含推进规则) 并下调两个阈值。

不选的接缝: 起真实会话看 AI 会不会自动推进 (不可重复, 且把模型行为写进断言必然长期不稳)、
断言文案里某句话在第几行 (实现细节, 措辞本就要随经验调)。
