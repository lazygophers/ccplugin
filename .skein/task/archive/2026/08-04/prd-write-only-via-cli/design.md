# prd 只读, 写入收归 CLI — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 现状: 门要求七章, CLI 只能写三章

这不是「顺手补个白名单」, 是本任务的**前置条件**。confirm 门校验 prd 七个二级章节齐备且顺序一致,
而章节写入 CLI 的白名单只有三章 —— 其余四章目前**只能靠直接编辑文件填**。

也就是说, 现状下 prd 能写完, 恰恰是因为没加锁。先加锁再补白名单, 中间那段时间 prd 直接变成
填不完的死局。所以顺序是硬的: **先扩写入路径, 再上锁**。这条已编码进 subtask 依赖, 不靠执行者自觉。

这个缺口在 `cli-usage-selfevident` 任务里被记录过但判为超范围 (那次的边界是「只改表达不改能力」),
本次是它的正式偿还。

## 加锁机制: 复用既有名单, 不另起一套

拦截层已有一份「脚本管理文件」名单, 命中的文件由守卫硬阻编辑类工具、且不被授权层放行 ——
任务元数据文件走的就是这条路。prd 加入同一份名单即可, **不新增第二套判断**。
两套并行的拦截逻辑必然各自漂移, 这是要避免的主要风险。

注意这层的两个 hook 是配合工作的: 授权层负责「不主动放行」, 守卫层负责「硬阻」。名单同时被两处
读取, 所以只需改名单本身。

## 关键取舍

- **只锁 prd, 不锁详细设计与调研收敛**: 用户要的是 prd。详细设计是自由文本, 没有章节 schema,
  也就没有「结构合法性」这个加锁理由 —— 为它加锁只是徒增摩擦。
- **索引章节不开放写入**: 它是模板固定的链接区, 开放等于允许破坏索引结构。写入白名单扩到门要求
  的其余全部章节, 唯独排除它。
- **拦截文案必须给可照抄的命令**: 这是本次的重点而非附带。只说「禁止编辑」会让调用方开始试错 ——
  这正是 `cli-usage-selfevident` 处理过的那类「首调必失败」问题, 不能在这里再造一个。
  文案里的命令形态要与真实 CLI 一致, 且应被仓内既有的「文档命令有效性」扫描覆盖。
- **用户故事章节的格式例外要保住**: 它的条目是固定编号叙述而非可勾选条目, 写入层已有对应处理,
  扩白名单时不得把它并进「可勾选章节」那一组。
- **引擎内部写盘不受影响**: 拦截只针对外部编辑工具的调用载荷, 引擎生成模板与写章节走内部路径,
  天然绕开。这一条要验证而不是假定。

## 自举说明 (dogfooding)

本任务的 prd 与详细设计是在加锁前用直接编辑写的。锁生效后, 后续任务的 prd 只能经 CLI 填 ——
这正是本次要验证「七章无死角」的现实理由: 验证不过, 下一个任务就建不起来。

## 测试接缝 (seam)
check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

**接缝 = 拦截层的载荷进/判定出** (喂一个工具调用载荷, 断言放行或拦下、拦下文案含替代命令),
**外加一条端到端**: 在临时工作区从建任务跑到 confirm 过门, 全程只用 CLI 填章节。

为什么破例用两个: 前者覆盖「锁住了没有」, 后者覆盖「锁住之后还填得完吗」—— 这是本任务两个
互相独立且都可能单独失败的方向, 一个接缝盖不住。端到端那条同时是「无死角」唯一的证伪方式。

不选的接缝: 断言白名单常量的元素个数 (实现细节, 正是本次要改的东西)、手工在真实仓库里试编辑
(不可重复, 且会污染真实任务数据)。
