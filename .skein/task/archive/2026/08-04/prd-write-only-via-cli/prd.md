# prd 只读, 写入收归 CLI — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标
要解决什么 / 用户价值 / 成功长什么样:
- [ ] prd 文件不再被直接编辑, 全部写入经 CLI —— 结构与章节顺序由引擎保证, 不靠调用方自觉
- [ ] CLI 的章节写入能力覆盖 confirm 门要求的全部章节, 不留「门要求填但没有写入路径」的死角
- [ ] 被拦时给出可照抄的替代命令, 调用方一次就能改对, 不靠试错

## 边界
范围内 / 范围外 (非目标) / 已知约束:
- [ ] 范围内: prd 文件的直接编辑拦截、章节写入白名单扩到门要求的全部章节、拦截时的指路文案
- [ ] 范围外: 其他 planning 工件 (详细设计 / 调研收敛) 不加锁, 本次只管 prd; 不改 confirm 门的校验口径; 不改章节名与顺序
- [ ] 约束: **必须先有写入路径再上锁** —— 反过来做会把 prd 变成填不完的死局, 现状正是门要求七章而 CLI 只能写三章
- [ ] 约束: 索引章节是模板固定的链接区, 不开放写入 (放开等于允许破坏索引结构)
- [ ] 约束: 拦截只针对外部编辑工具; 引擎自身生成模板与写章节走内部路径, 不受影响
- [ ] 约束: 用户故事那一章的条目格式与其他章节不同 (固定编号叙述而非可勾选条目), 写入时不得被折成勾选框

## User Stories
极其详尽地穷举, 覆盖功能各方面 (含边界情况) —— 穷举本身就是逼出边界情况的机械手段:
1. As a AI 调用方, I want 直接编辑 prd 时被明确拦下, so that 不会写出结构不合法的 prd 让后续校验才报错
2. As a AI 调用方, I want 拦截提示里直接给出该用的命令形态, so that 不用先去翻帮助再猜参数
3. As a AI 调用方, I want 门要求的每一章都能经命令写入, so that 不会遇到「填不进去又过不了门」的死局
4. As a AI 调用方, I want 整章重写与追加条目两种方式都在, so that 初次成稿与后续增补都不用手动拼接全文
5. As a AI 调用方, I want 用户故事章节写入后保持其固定编号格式, so that 不被误折成勾选条目破坏格式
6. As a AI 调用方 (边界), I want 写入不存在的章节名时报错并列出合法章节名, so that 立刻知道自己拼错了哪个
7. As a 用户, I want 引擎自己生成 prd 模板不受拦截影响, so that 建任务这条主路不被自己的锁堵死
8. As a 用户, I want 只读 prd 不受影响, so that 查看内容仍然自由
9. As a 维护者, I want 拦截规则与既有的同类拦截共用一套机制, so that 不出现两套并行的拦截逻辑各自漂移

## 验收标准
可执行、可核对的完成断言 (逐条):
- [ ] 用编辑类工具直接改 prd 会被拦下, 且拦截信息里含可照抄的替代命令
- [ ] 读 prd 不受影响
- [ ] confirm 门要求的每一章都能经命令写入与追加, 无死角
- [ ] 索引章节不在开放写入之列
- [ ] 用户故事章节经命令写入后保持其固定编号格式, 未被折成勾选条目
- [ ] 写入不存在的章节名时报错并列出合法章节名
- [ ] 引擎生成模板与内部写章节不受拦截影响
- [ ] 拦截复用既有同类机制, 无第二套并行实现
- [ ] 全量 pytest 不低于基线 410 passed / 0 failed

## 验证方式
每条验收标准的验证手段与通过标准 (plan 阶段必填):
- [ ] 拦截生效: 构造一次编辑类工具调用打向 prd, 看拦截结果 —— 通过标准: 被拒, 且输出含替代命令形态
- [ ] 读不受影响: 同法构造一次读调用 —— 通过标准: 放行
- [ ] 无死角: 在临时工作区逐章实跑写入与追加, 走到 confirm 通过为止 —— 通过标准: 七章全填得进去且 confirm 过门
- [ ] 索引不开放: 尝试写索引章节 —— 通过标准: 被拒并列出合法章节名
- [ ] 格式保持: 写完用户故事章节后读回 —— 通过标准: 仍是固定编号格式, 无勾选框
- [ ] 错误可读: 写一个拼错的章节名 —— 通过标准: 报错文本含全部合法章节名
- [ ] 引擎不自堵: 建一个新任务 —— 通过标准: 模板正常生成
- [ ] 单一机制: 读拦截实现 —— 通过标准: prd 与既有被拦文件走同一份名单与同一处判断
- [ ] 回归: `uv run pytest plugins/tools/skein/scripts/tests/` —— 通过标准: 410 passed / 0 failed

## Testing Decisions
什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:
- [ ] 好测试 = 从**拦截层的输入输出**断言: 喂一个工具调用的载荷进去, 断言放行还是拦下、拦下时文案含不含替代命令。这是拦截层真实的调用面
- [ ] 第二个接缝是**在临时工作区跑通七章填写到 confirm 过门**的端到端路径 —— 它是唯一能证伪「没有死角」的方式, 也正是现状缺口的反面
- [ ] 不测: 章节白名单常量里有几个元素、拦截判断写在哪个函数 —— 属实现细节
- [ ] 先例: 仓内既有针对 hook 层与 CLI 章节读写的测试, 沿用同一形态
- [ ] 拦截文案里的命令形态必须与真实 CLI 一致 —— 仓内已有扫描文档命令有效性的测试, 拦截文案同属「会被照抄执行」的文本, 应纳入同类校验
