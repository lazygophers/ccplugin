# 看板页头: 总进度条 + 总剩余时间 — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 1. 这不是新功能, 是接线

两个算法都已存在且在概览页跑着:
- **加权总进度**: 按 estimate 加权的完成度; 无 estimate 的 task 退化为等权 (不因为没估工时就被
  排除在分母外)
- **聚合 ETA**: 取「关键路径长度」与「总工时 ÷ 并发数」的较大者作墙钟下界 —— 回答的是「还要多久」,
  不是「一共多少人时」

所以本 task 的实质是**把看板页的取数路径接到同一组函数上**, 外加一条进度条的渲染。任何「顺手改进
一下算法」的念头都不属于本 task —— 那会让两个页面短暂地各算各的, 而这正是最坏的失败模式。

## 2. 关键取舍: 数据从哪来

概览页有专供聚合的精简字段。看板页自己已经拿了全量 task 列表 (它要画 DAG)。

**取舍**: 优先用看板页手上已有的全量列表算, 不为此新增端点或新增请求。理由 —— 看板已经把数据取
全了, 再发一次请求只为了拿同样的数, 是纯粹的浪费; 而且两次请求之间数据可能变, 反而制造出「进度条
和 DAG 对不上」的诡异现象。

只有在确认看板现有数据缺少算法所需字段 (如 estimate / progress / deps) 时, 才补端点字段 —— 补
字段也优于新开端点。

## 3. 口径歧义: 筛选不影响总进度

看板有状态筛选栏。筛掉一半 task 之后, 页头的进度条**仍应显示全量口径**。

理由: 「整体进度」问的是项目整体, 不是当前视野。但这会造成一个真实的困惑 —— 用户筛出 3 个 task,
却看到一个 42% 的进度条, 会以为是这 3 个的进度。所以口径必须在界面上说清楚 (副文本注明总数),
不能只靠「我们知道它是全量」。

## 4. 布局

页头现有四块: 标题区 / 状态筛选栏 (flex-1) / DAG 视图控件 / 清理按钮 + 视图切换。

进度条塞进标题区下方最稳 —— 那里现在只有一行小字 (`N 个任务 · M 个高亮`), 纵向有空间, 且不与
flex-1 的筛选栏抢横向宽度。窄屏时筛选栏本就换行, 进度条跟着标题区走不会让情况更糟。

## 5. 边界文案

| 场景 | 进度 | 剩余 |
|---|---|---|
| 无 task | 0% (条为空) | 暂无任务 |
| 全部完成 | 100% | 全部完成 |
| 全部未估工时 | 正常显示 (等权退化) | 未知 (标明 N 个未估) |
| 部分未估工时 | 正常显示 | 正常显示 + 「N 个未估工时」提示 |

「未知」与「0」必须区分开 —— 显示 0h 剩余会让人以为马上做完, 这比不显示更有害。

## 6. 已知风险

- **两页不同源**: 若图省事在看板里另写一份计算, 两个百分比迟早分叉。对策见测试接缝 —— 用一致性
  测试钉死。
- **悬空引用**: 本仓库已踩过两次 (`fmtHours`、`deltaText`) —— 函数没导出 / 没导入, 测试全绿但
  运行时炸。对策: 复用现有的 JS 导出导入静态扫描守卫, 新增引用必须被它覆盖。

## 测试接缝 (seam)

check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

**接缝 = 算法函数的输入输出 (纯函数层)**, 复用现有 JS 测试的既有做法, 不新建。

理由: 页头要显示的两个数完全由这两个纯函数决定, 给定一组 task 数据它们的输出是确定的。在这一层
断言, 覆盖了全部边界场景 (无 task / 全完成 / 全未估), 且完全不碰 DOM —— 改样式、换布局、调 class
都不会让测试变红。

**一致性测试也落在同一接缝**: 同一份数据分别走概览页与看板页的取数路径, 断言两者传给算法的输入
等价、算出的百分比相等。这是本 task 唯一真正要防的失败模式。

**不新建 DOM 层接缝**: 不为进度条渲染写 DOM 断言。渲染对不对靠人眼看一次即可, 而 DOM 断言的维护
成本会持续存在且几乎必然过期。唯一的自动化保障是那条静态导出/导入扫描 —— 它防的是运行时炸, 不是
样式对不对, 二者不可互相替代。
