# 看板页头: 总进度条 + 总剩余时间 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标

看板是盯进度的主界面, 但页头只有「N 个任务 · M 个高亮」—— 两个数都答不上使用者真正要问的那两个
问题: **整体走了多远**、**还要多久**。想知道就得切到概览页, 而概览页看不到 DAG, 于是来回切。

这两个数的算法**已经写好了** (加权总进度 + 按并发折算的墙钟剩余), 概览页正在用。本 task 只是把
同一套算法接到看板页头, 并把总进度以进度条形式呈现 —— 数字告诉你百分比, 进度条让你不用读数字。

成功长这样: 打开看板, 页头一眼看到「整体 42% · 预计剩余 6.5h」并有一条进度条; 这两个数与概览页
显示的完全一致 (同一套算法, 不是各算各的)。

## 边界

范围内 / 范围外 (非目标) / 已知约束:

**范围内**
- [ ] 看板页头新增: 加权总进度条 (含百分比) + 墙钟总剩余时间
- [ ] 复用已有的加权进度与聚合 ETA 算法, 不新写一套
- [ ] 副文本给出口径说明 (总工时、并发数、未估工时的 task 数)

**范围外 (非目标)**
- [ ] 不改算法本身 (权重口径、墙钟折算方式都不动)
- [ ] 不改概览页 (它已经有了)
- [ ] 不动 markdown 看板 (本 task 只管 Web 看板页)
- [ ] 不新增后端端点 —— 看板现有数据源已含所需字段就直接用, 缺字段才补

**已知约束**
- [ ] 进度条必须与页头现有元素 (标题、状态筛选栏、视图切换、清理按钮) 共存, 且不挤爆窄屏布局
- [ ] 两处 (概览页 / 看板页) 必须同源同算 —— 出现两个不一样的百分比, 比不显示更糟

## User Stories

极其详尽地穷举, 覆盖功能各方面 (含边界情况):

1. As a 盯进度的人, I want 看板页头显示整体完成百分比, so that 我不用切到概览页。
2. As a 盯进度的人, I want 那个百分比配一条进度条, so that 我扫一眼就知道大概位置, 不必读数字。
3. As a 盯进度的人, I want 页头显示预计剩余时间, so that 我知道还要多久, 而不只是知道做了多少。
4. As a 谨慎的人, I want 剩余时间旁能看到口径 (总工时 / 并发数), so that 我知道这是墙钟不是人力工时。
5. As a 谨慎的人, I want 知道有几个 task 没估工时, so that 我判断这个剩余时间可不可信。
6. As a 边界情况, 全部 task 已完成时剩余显示「全部完成」而非 0h 或空白。
7. As a 边界情况, 一个 task 都没有时显示「暂无任务」而非 NaN / 0%。
8. As a 边界情况, 全部 task 都没估工时时进度条仍能显示 (退化等权), 剩余标为未知而非 0。
9. As a 窄屏用户, I want 页头在窄屏下仍可用, so that 进度条不会把筛选栏挤到看不见。
10. As a 对账的人, I want 看板与概览页的百分比完全一致, so that 我不用怀疑哪个是对的。
11. As a 筛选中的人, I want 明确知道总进度是**全量**口径而非当前筛选结果的口径, so that 我不会
    把筛掉一半后的百分比误当整体进度。

## 验收标准

可执行、可核对的完成断言 (逐条):

- [ ] 看板页头显示加权总进度百分比 + 进度条
- [ ] 看板页头显示墙钟总剩余时间
- [ ] 剩余时间附口径说明: 总工时、并发数、未估工时 task 数 (为 0 时不显示该段)
- [ ] 进度与剩余两个数与概览页在同一份数据下**完全一致** (同源同算)
- [ ] 总进度口径为全量 task, 不随状态筛选变化, 且这一点在界面上不产生歧义
- [ ] 全部完成 / 无任务 / 全部未估工时 三种边界各有明确文案, 无 NaN / 空白 / 误导性的 0
- [ ] 窄屏下页头不塌 (进度条让位, 筛选栏与视图切换仍可点)
- [ ] 现有页头元素 (任务数、高亮数、状态筛选、视图切换、清理已完成) 功能不回归
- [ ] 前端无 console 报错 (含已修过的那类「函数未导出 / 未导入」悬空引用)
- [ ] 全量测试通过, ruff F/E9 清白

## Testing Decisions

什么算好测试 / 测哪些模块 / codebase 内的同类测试先例:

算法本身已有归属, 本 task **不重复测算法** —— 只测「看板页头是否正确消费了算法输出」。

好测试 = 给一组 task 数据, 断言页头渲染出的百分比 / 剩余文案符合预期, 三个边界各一条。不测 DOM
结构细节 (class 名、嵌套层级), 那是实现细节, 改个样式就红。

同源一致性用一个测试钉死: 同一份数据分别喂给概览页与看板页的取数路径, 断言两者算出的百分比相等。
这条比任何 UI 断言都重要 —— 两个页面显示不同的进度是最坏的失败模式。

沿用仓库现有的 JS 静态守卫先例 (导出 / 导入绑定扫描), 确保新加的引用不会变成运行时才炸的悬空引用
—— 这类 bug 本仓库已经踩过两次 (`fmtHours`、`deltaText`), 测试全绿也拦不住。
