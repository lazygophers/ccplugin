# .skein 衍生物忽略清单与生成器对齐 — 详细设计

架构 / 数据流 / 关键取舍 / 技术选型 (不含调度图, 调度归 task.json):

## 测试接缝 (seam)

check 阶段验证的是`行为对不对`而非`跑没跑起来`, 全靠这里选对接缝。三条规则:
1. 优先复用现有接缝, 不新建
2. 取最高接缝 (越靠外部行为越好)
3. 越少越好, 理想 = 1 个

**接缝 = 「全新工作区初始化 → 跑一遍会产生衍生物的命令 → 版本库状态干净」。**

这是最高接缝, 因为它就是用户真正在意的事实。往下钻 (断言忽略文件里有某一行) 是测实现:
条目怎么写、分几行、用什么通配符, 全是本 task 要改的东西, 钉住它们等于钉住改动本身。

复用性: 仓库已有忽略文件生成 + 幂等补缺的测试, 本设计把它抬到这个更高的接缝上, 不另起一套。

## 真值源: 以代码写盘点为准 (用户 2026-08-01 定调)

**当前项目那份忽略文件不作参照** —— 它被人手工补过, 只救了这一个仓库, 反而掩盖了生成器的缺陷。
判断依据只有一个: **代码里有没有产出它的写盘点, 以及它有没有重建路径。**

勘察已确认漂移是双向的:

| 方向 | 表现 |
|---|---|
| 漏 | hook 计数标记、索引聚合类产物有写盘代码, 生成器清单里没有 |
| 多 | 有一条目标文件全库搜不到写盘点, 属历史残留 |

## 核心取舍: 怎么让清单不再漂

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 补几行了事 | 把漏的补进写死清单 | 修的是这一次的症状, 下次加衍生物照样漏 —— **用户要的是「确保逻辑一致」, 不是补丁** |
| **B. 单一登记处 + 守卫** | 衍生物在一处登记, 清单由它导出; 守卫扫未登记的写盘点 | 根治漂移; 需要先定义清楚「什么算衍生物」 |
| C. 运行时探测 | 跑一遍看产出了什么就忽略什么 | 覆盖不全 (条件分支产物跑不到), 且把「该不该入库」变成偶然结果 |

**取 B。** A 是把同一个坑填一次, 而这个坑的性质就是「会反复出现」—— 它已经漂过一次了。
C 看着聪明, 实际上让正确性依赖于测试恰好覆盖到哪条分支, 不可靠。

## 最危险的地方: 衍生物 vs 真值

同一个工作区目录下两类文件混住:

- **衍生物** —— 有重建路径, 忽略它只是让仓库干净
- **真值** —— 用户的任务数据, 忽略它等于**数据不进版本库**

判错方向的代价严重不对称: 少忽略一个衍生物 = 仓库脏一点; 多忽略一个真值 = 用户丢工作。
**因此判据必须是「有没有一条命令能从真值重新产出它」, 而不是靠文件名或位置猜。**
拿不准时一律判为真值 (不忽略) —— 往安全的一侧取。

真值不被误忽略需要独立断言逐条钉死, 不能只靠人眼复查 (PRD Testing Decisions 已列)。

## 防漂移守卫

守卫要能发现「新增了衍生物写盘点却没在登记处登记」。用源码扫描 (仓库有先例), 而非运行时探测,
理由同上: 条件分支里的写盘点跑不到, 但扫得到。

**必须反向验证**: 故意加一个未登记的衍生物写盘点, 确认真的变红, 再撤掉。
没红过的守卫等于没有守卫 —— 而这个 task 存在的原因, 正是上一版清单没有任何守卫。

## 兼容既有工作区

保留现有的幂等补缺行为: 缺行则补, 不覆盖用户手写条目, 条目齐全时零改动。
移除残留条目要谨慎 —— 用户的忽略文件里可能有他自己加的同名行, 移除逻辑只对生成器自己产的条目生效。
