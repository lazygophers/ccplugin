# .skein 衍生物忽略清单与生成器对齐 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标

初始化工作区时会生成一份忽略清单, 用来把「脚本自己产的、能重建的东西」挡在版本库外。
这份清单是**写死的常量**, 而产生衍生物的写盘点散落在十几个模块里 —— 两者之间没有任何强制关联,
于是必然漂移, 而且已经漂了, 两个方向都漂:

- [ ] **清单漏了真实产物**: 有若干每次重建索引就会重写的聚合文件、以及一对 hook 计数标记文件,
      写盘代码明明在跑, 清单里没有。新初始化的工作区会把它们当成用户文件提交进版本库。
- [x] ~~**清单留着不存在的产物**~~ —— **g1 勘察后证伪 (main 已复核)**。生成器清单 `GI_ENTRIES`
      当前 8 条**全部有效, 无残留**。原以为无写盘点的 `vision.md` 实际有 (`store.py:245 _write_vision`)。
      唯一那条 `board/` 只存在于**本仓库手补的**忽略文件里, 从未被生成器产出 (全库 `board` 仅作 CLI
      子命令名, 无目录创建点; 磁盘无该目录)。
      **后果: g3 收敛为「只补漏, 不做任何移除」** —— 生成器无法区分 `board/` 与用户手写条目,
      删它就是动用户的东西, 与 design.md「移除逻辑只对生成器自己产的条目生效」一致。

本仓库表面上没暴露问题, 是因为有人在历史上手工往忽略文件里补过几行 —— 但那份手补的文件
**只救了这一个仓库**, 生成器没改, 所以每个新工作区都会重新踩一遍。

用户明确定调: **以代码的实际写盘点为准, 不以当前项目那份手补文件为准。**

成功长这样: 忽略清单与代码实际产出同源, 新工作区一次初始化就完整覆盖; 以后任何人加一个新的
衍生物写盘点却忘了登记, **当场测试变红**, 而不是等某个仓库脏了才发现。

## 边界

范围内 / 范围外 (非目标) / 已知约束:

**范围内**
- [ ] 穷举代码里所有产生「可重建/临时」产物的写盘点, 得出真值清单
- [ ] 让生成的忽略清单与该真值同源, 消除写死常量与实际产出各行其是的局面
- [ ] 补齐当前漏掉的衍生物; 移除代码里已无写盘点的残留条目
- [ ] 机械守卫: 新增衍生物写盘点却未登记 → 测试失败
- [ ] 既有工作区能通过幂等补缺拿到修正后的清单 (不破坏用户手写条目)

**范围外 (非目标)**
- [ ] 不改任何衍生物的生成逻辑、路径、格式 —— 只改「它该不该入库」的声明
- [ ] 不动 worktree 目录写进仓库根忽略文件的那条既有机制
- [ ] 不清理已经被误提交进版本库的历史文件 (那是独立的一次性清理)
- [ ] 不引入新的配置项让用户自定义忽略清单

**已知约束**
- [ ] **必须区分「衍生物」与「真值」**。同在工作区目录下, 有的是可重建产物 (该忽略),
      有的是唯一真值 (绝不能忽略 —— 忽略了等于用户的任务数据不进版本库)。判据要写清楚,
      这是本 task 最危险的地方: 判错方向不是少忽略一个文件, 而是丢数据。
- [ ] 幂等补缺不能破坏用户在忽略文件里手写的条目。
- [ ] 移除残留条目要谨慎: 「代码里搜不到写盘点」有可能是搜漏了而非真的没有。移除前需正面确认。
- [ ] 判断某条产物是否可重建, 依据是它有无重建路径 (某个命令能从真值重新产出它), 不是靠命名猜。

## User Stories

极其详尽地穷举, 覆盖功能各方面 (含边界情况):

1. As a 新建工作区的人, I want 一次初始化就把全部衍生物挡在版本库外, so that 我不用手工补忽略行。
2. As a 已有工作区的人, I want 升级后跑一次初始化能补上缺的条目, so that 老仓库也能修好。
3. As a 已有工作区的人, I want 补缺不动我手写的条目, so that 我的自定义忽略不被覆盖。
4. As a 以后要加新衍生物的开发者, I want 忘记登记时被测试拦住, so that 清单不会再次悄悄漂移。
5. As a 维护者, I want 清单里不留代码已不产出的条目, so that 我读它时不会被误导去找不存在的文件。
6. As a 使用者, I want 任务数据这类唯一真值绝不被忽略, so that 我的工作不会没进版本库。
7. As a 边界情况, 衍生物与真值同目录甚至同后缀时, 判据仍要能把它们分开。
8. As a 边界情况, 某衍生物只在特定功能开启时才产生, 它也要被覆盖, 而不是等有人开了才发现漏。
9. As a 边界情况, 忽略文件被用户删掉后重跑初始化, 应当完整重建而不是只补差量。
10. As a 边界情况, 忽略文件已存在且条目齐全时, 重跑初始化不应产生任何改动 (真幂等)。
11. As a 审阅者, I want 看得出哪些条目是新补的、哪些是移除的及其理由, so that 我能核对判断对不对。

## Testing Decisions

什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:

**最高接缝是「跑完命令后版本库干净不干净」**, 不是「忽略文件里有没有某一行」。后者测的是实现,
一改措辞就红; 前者测的是用户真正在意的事实。仓库已有针对忽略文件生成与幂等补缺的测试先例,
**沿用并扩到这个更高的接缝上**。

**防漂移守卫是本 task 的核心产出, 不是附属品**。清单已经漂过一次, 说明「靠人记得同步」不成立。
守卫要能发现「新增了衍生物写盘点却没登记」。仓库对源码文本扫描类守卫已有先例, 手法可复用。
守卫**必须反向验证**: 故意加一个未登记的写盘点, 确认真的变红。没红过的守卫等于没有守卫。

**真值不被误忽略要有专门断言**。这是本 task 唯一会造成数据损失的失败模式, 靠人眼复查不够 ——
必须逐条钉死: 任务真值类文件在任何情况下都不匹配忽略规则。

**不测**: 不测忽略文件的行序、注释文案、条目写法。那些是实现细节, 而调整它们正是本 task 要做的事。
