# hook 层一 hook 一文件 — PRD (主入口)

> 禁写具体文件路径与代码片段 (会很快过期) —— 例外: prototype 产出的能精确编码决策的片段 (状态机/schema/type shape) 可内联, 且须注明来自 prototype。

## 目标
要解决什么 / 用户价值 / 成功长什么样:
- [ ] 一个 hook 一个文件, 找某个 hook 的实现不再需要先知道它被塞在哪个合并模块里
- [ ] 懒加载名副其实: 调某个 hook 只加载它自己那条链, 不再连带付同文件里其他 hook 的常量与正则的代价
- [ ] 分层说明与实际文件结构一致, 不留过时的划分口径

## 边界
范围内 / 范围外 (非目标) / 已知约束:
- [ ] 范围内: 把装了多个 hook 的模块按 hook 拆开, 私有常量与 helper 随各自 hook 走, 跨 hook 共用的少数常量下沉到公共零件模块; 子命令分发表同步改指; 分层说明更新
- [ ] 范围外: 非 hook 的基础设施模块 (分发、公共零件、钩子执行器、复杂度判定纯函数) 不拆不动; 不改任何 hook 的行为与判据; 不改对外入口路径与子命令名
- [ ] 约束: **行为一字不变** —— 纯搬迁, 不借机重构逻辑、不合并重复代码、不优化措辞
- [ ] 约束: hook 层是每个 prompt 都跑的最热路径, 拆完 import 开销不得劣化
- [ ] 约束: 对外契约固定 —— 入口文件路径与全部子命令名是插件配置里写死的, 一个都不能改

## User Stories
极其详尽地穷举, 覆盖功能各方面 (含边界情况) —— 穷举本身就是逼出边界情况的机械手段:
1. As a 维护者, I want 按 hook 名就能直接定位到文件, so that 不用先读分层说明才知道它在哪
2. As a 维护者, I want 某个 hook 的常量与私有 helper 就在它自己文件里, so that 改它时不必担心影响同文件的其他 hook
3. As a 用户, I want 授权类 hook 只加载自己那条链, so that 每次授权不为不相关的 hook 付加载成本
4. As a 用户, I want 拆分后每个 prompt 的 hook 开销不比拆分前高, so that 结构整洁不以速度为代价
5. As a 维护者 (边界), I want 真正被多个 hook 共用的少数常量有明确归属, so that 不出现两份副本各自漂移
6. As a 维护者 (边界), I want 只被单个 hook 使用的 helper 整条链跟着它走, so that 公共零件模块不被塞成杂物间
7. As a 用户, I want 全部子命令拆分前后逐条都还能调用, so that 插件配置里的 hook 接线不断
8. As a 维护者, I want 分层说明改成与新结构一致, so that 下一个人不被过时的划分口径误导

## 验收标准
可执行、可核对的完成断言 (逐条):
- [ ] 装多个 hook 的两个模块已删, 每个 hook 各有独立文件
- [ ] 每个新文件只含自身 hook 的代码, 私有 helper 整条链随其归属 hook
- [ ] 跨 hook 共用的常量只有一份, 位于公共零件模块
- [ ] 子命令分发表逐条改指到位, 全部子命令可调用
- [ ] 行为零变更 —— 搬迁前后逐函数比对, 差异仅限 import 语句与文件位置
- [ ] 热路径 import 开销不劣于拆分前
- [ ] 分层说明与实际文件结构一致
- [ ] 全量 pytest 不低于基线 410 passed / 0 failed

## 验证方式
每条验收标准的验证手段与通过标准 (plan 阶段必填):
- [ ] 拆分完成: 列目录 + 读分发表 —— 通过标准: 每个子命令指向一个专属文件, 原合并模块不存在
- [ ] 归属正确: 对每个私有 helper 与常量 grep 其使用点 —— 通过标准: 单 hook 使用的与其 hook 同文件, 多 hook 使用的在公共零件模块且仅一份
- [ ] 行为零变更: 与搬迁前的 git 版本逐函数比对 —— 通过标准: 函数体逐字一致, 差异仅 import 与位置
- [ ] 子命令可调用: 逐条实调全部子命令 (给合法输入, 看不报错且返回预期退出码) —— 通过标准: 全部成功, 无 ImportError / AttributeError
- [ ] 热路径开销: 用 `python3 -X importtime` 量入口 import 耗时, 与拆分前同法测得的基准比 —— 通过标准: 不高于基准
- [ ] 分层说明: 读说明与列目录对照 —— 通过标准: 说明列出的模块与实际文件一一对应
- [ ] 回归: `uv run pytest plugins/tools/skein/scripts/tests/` —— 通过标准: 410 passed / 0 failed

## Testing Decisions
什么算好测试 (只测外部行为不测实现细节) / 测哪些模块 / codebase 内的同类测试先例:
- [ ] 纯搬迁任务, 「好测试」= 复用既有护栏证明外部行为没变, 不为搬迁新建单测
- [ ] 最有价值的一条是**逐条实调全部子命令**: 它测的是「从命令行喂输入进去还能不能跑」这一最外层行为, 一次覆盖 import 接线、分发表、函数可达性三类搬迁事故
- [ ] 不测: 某个常量定义在哪个文件、import 语句写法 —— 属实现细节, 正是本次要改的东西
- [ ] 行为零变更靠与 git 旧版本逐函数比对, 不写成断言 (函数体会随后续正常演进漂移, 写死即脆)
- [ ] 既有护栏: 仓内已有覆盖 hook 层的测试, 搬迁后必须仍绿
- [ ] 热路径开销有明确的历史基准值记录在分层说明里, 沿用同一测法可比
